# Introducing ExtendDB

## Transcript

Welcome.  It  is  a  pleasure  to  introduce Extend  DB,  an  innovative  open-source solution  designed  to  bridge  the  gap between  the  familiar  Dynamo  DB  API  and  a wide  variety  of  storage  requirements.  As illustrated  by  the  bridge  in  our  visual, extend  DB  acts  as  a  powerful  adapter that  provides  the  flexibility  of pluggable  storage  backends.  This  allows developers  to  maintain  the  seamless experience  of  Dynamo  DB  while  gaining the  freedom  to  choose  the  underlying infrastructure  that  best  fits  their specific  performance,  cost  or  compliance needs.  We  are  excited  to  show  you  how Extend  DB  can  help  you  extend  your database  capabilities  with  ease.  The boundary  of  cloudnative  development  is often  defined  by  a  stark  divide  between central  infrastructure  and  the operational  edge.  Within  the  cloud,  we leverage  powerful  services  like  Amazon Dynamo  DB,  which  demand  deep  expertise in  data  modeling,  CI  pipelines,  and rigorous  operational  runbooks  to function  effectively  at  scale.  However, as  we  move  toward  the  edge,  we  encounter the  rewrite  barrier.  In  the  absence  of  a compatible  runtime,  development  teams are  forced  into  the  inefficient  position of  maintaining  two  separate  application stacks  and  two  distinct  data  access layers.  This  fragmentation  creates  a significant  hurdle  for  engineering velocity  and  modernization. At  the  edge,  the  operational requirements  shift  toward  extreme reliability  and  performance.  Critical systems  such  as  gate  and  onboard aviation  applications  must  maintain  full functionality  through  network  outages and  cannot  tolerate  the  latency  inherent in  a  cloud  roundtrip.  To  truly  master cloudnative  development,  we  must  find ways  to  transcend  this  barrier  and provide  a  consistent  execution environment  from  the  data  center  to  the furthest  reaches  of  the  network.  Extend DB  serves  as  a  structural  bridge  for your  data  access  layer,  enabling applications  to  communicate  using  the DynamoB  JSON  protocol  via  standard  AWS SDKs.  At  the  center  of  this  architecture is  Extend  DB  acting  as  a  translator written  in  Rust.  It  seamlessly  converts the  Dynamo  DB  wire  protocol  into standard  SQL  commands.  This  translation layer  allows  Postgress  to  function  as  a reference  backend  where  it  handles actual  data  storage.  By  using  Postgress, you  can  leverage  a  suite  of  familiar  and powerful  administrative  tools  such  as  PG dump  replication  and  point  in  time recovery.  Extend  DB  is  released  under the  Apache  2.0  no  license  providing  a performant  and  open-source  solution  for bridging  these  two  database  paradigms. ZeroCloud  dependency  for  disconnected scenarios  allows  you  to  decouple  your applications  from  specific  cloud providers,  providing  flexibility  across various  environments.  Starting  with local  development  and  CI/CD,  you  can  run workloads  directly  on  your  laptop.  This ensures  that  integration  tests  start  in seconds,  run  deterministically,  and  tear down  cleanly  without  the  need  for  an active  internet  connection  or  cloud account.  Moving  to  on  premises  and airgapped  environments.  This  approach enables  developers  and  edge  operators  to work  without  cloud  connectivity.  You  can execute  Dynamo  DB  access  patterns  on your  own  infrastructure,  ensuring operational  consistency  even  in  the  most isolated  locations.  Finally,  for multicloud  and  hybrid  scenarios,  this model  facilitates  true  portability across  infrastructure  providers.  By leveraging  the  Dynamo  DB  API  anywhere Postgress  is  available,  you  can experiment  with  different  providers  such as  AWS,  Azure  or  GCP  or  even  run  on  your private  cloud.  This  effectively eliminates  vendor  lockin  and  provides  a unified  interface  for  your  data regardless  of  the  underlying  host. Extend  DB  implements  the  Dynamo  DB  wire protocol  which  allows  it  to  function  as a  seamless  drop-in  replacement  within your  existing  architecture.  As  you  can see  in  the  code  snicker,  integrating Extend  DB  only  requires  a  simple  change to  your  endpoint  URL  configuration.  This compatibility  ensures  that  your  current application  code,  AWS  SDKs,  and  CLI tooling  can  connect  to  Extend  DB entirely  without  modification.  Instead of  sending  requests  to  the  cloud,  your tools  communicate  directly  with  a  local port  such  as  port  8000,  allowing  for  a smooth  transition  and  consistent development  experience.  Let's  take  a look  under  the  hood  at  the  architectural design  of  the  extend  DB  binary,  which  is built  on  the  fundamental  principle  of separation  of  concerns.  When  an  incoming HTTP  request  arrives,  it  is  first handled  by  the  server  crate.  This  layer ties  the  entire  system  together  by managing  the  HTTP  server.  the  management API  and  the  web  console.  Once  processed by  the  server  layer,  the  request  moves to  the  engine  crate.  This  component  is dedicated  to  implementing  standard DynamoB  API  semantics,  ensuring compatibility  and  expected  behavior. Below  the  engine  lies  the  core  crate which  is  written  as  pure  synchronous Rust.  This  layer  is  responsible  for handling  types,  data  validation,  and expression  evaluation. Finally,  the  request  reaches  the  storage Postgress  crate.  This  represents  our back-end  implementation  which  is  built against  a  universal  storage  trait  to interface  directly  with  Postgress  crate. By  isolating  these  responsibilities  into distinct  crates,  we  ensure  a  modular maintainable  and  highly  robust  system. The  architecture  of  the  Extend  DB  engine is  built  around  a  central  concept  known as  the  pluggable  storage  trait.  By defining  the  storage  layer  as  a  flexible Rust  trait,  we  have  created  a  modular interface  that  decouples  the  core translation  engine  from  specific database  implementations.  Currently, Postgrescu  serves  as  our  version  0.1 reference  backend,  providing  a  stable foundation  for  initial  deployment  for environments  requiring  horizontal scalability.  This  V0.1 capability  dashboard  provides  a comprehensive  overview  of  the  core features  implemented  in  this  initial release.  Starting  with  table  operations, the  system  supports  full  administrative control,  including  the  ability  to create,  delete,  describe,  list,  and update  tables.  Moving  to  item  level interactions,  we  have  enabled  standard put,  get,  and  delete  operations alongside  a  robust  update  mechanism. This  supports  set,  remove,  add,  and delete  actions,  all  of  which  are compatible  with  complex  condition expressions  for  data  retrieval.  The query  and  scan  modules  are  fully operational  supporting  key  conditions, filter  expressions,  pagenation  and secondary  index  selection  to  optimize performance.  To  handle  high  volume  or atomic  operations,  we  have  integrated batch  and  transactional  support, specifically  batch  get  and  write  as  well as  transact  get  and  write  for  tasks requiring  AICD  compliance.  Regarding data  streams,  the  current  version  allows you  to  list  and  describe  streams  as  well as  retrieve  shard  iterators  and  records for  real-time  processing.  Finally,  the management  section  covers  essential administrative  functions  including  TTL configuration,  point  intime  import  and export  capabilities  and  resource tagging.  Extend  DB  implements  a  robust security  model  centered  on  mandatory  TLS and  local  SIGV4  authentication.  The process  begins  with  the  automatic generation  of  a  self-signed  certificate during  the  initial  run,  ensuring  all data  in  transit  is  encrypted.  For credential  management,  the  platform features  an  internal  AM  like  store  that operates  entirely  independently  from  AWS AM  allowing  for  secure  local  development without  external  dependencies.  Lastly, authentication  is  handled  through standard  SIGV4  signing.  By  utilizing  the exact  same  signing  logic  required  by managed  services,  your  application  can maintain  a  consistent  codebase  when moving  from  local  testing  to  cloud deployment.  In  this  comparison  of deployment  options,  we  evaluate  three tools.  Manage  Dynamob,  DynamoB  local, and  extend  DB  across  four  key  criteria. Managed  Dynamob  is  designed  for production  cloud  workloads  on  AWS.  As  a fully  managed  service  using  proprietary AWS  back-end  technology,  it  provides high  scale  and  reliability  with  minimal maintenance.  For  unit  testing,  DynamoB local  provides  a  lightweight  ephemeral environment.  It  runs  as  a  single  process in  memory  using  a  SQL  light  backend allowing  for  rapid  testing  cycles. Extend  DB  is  highlighted  as  a  versatile choice  for  local  development,  CI/CD pipelines,  and  edge  or  on  premises deployments.  It  can  be  deployed  on  any Linux  or  Mac  OS  infrastructure  and features  a  pluggable  architecture  that currently  utilizes  Postgress.  It  is  a self-managed  solution  necessitating  a database  administrator  for  its operation.  When  considering  Extend  DB, it  is  essential  to  understand  the architectural  boundaries  and  limitations inherent  in  its  design.  First,  it  is important  to  recognize  that  this  is  not a  managed  service.  Unlike  fully  managed cloud  solutions,  you  retain  full responsibility  for  database availability,  backups,  and  the  ongoing maintenance  of  the  underlying  Postgress engine.  Secondly,  there  are  significant performance  differences  to  keep  in  mind. The  performance  characteristics  and scaling  behavior  of  extend  will  differ from  native  AWS  managed  services.  It  is critical  to  understand  that  extend  DB  is designed  as  an  extension  and  is  not intended  to  be  a  direct  replacement  for DynamoB  in  high-scale  environments. Finally,  Extend  DB  does  not  support global  features.  Managed  capabilities specific  to  Dynamob  such  as  global tables  and  cross  region  replication  are not  implemented  here.  These  limitations should  be  carefully  weighed  against  your specific  operational  requirements  during the  architectural  planning  phase.  This architecture  embodies  the  write  once  run anywhere  philosophy  for  modern  data applications.  At  the  center  we  maintain a  single  application  codebase  and  a unified  CI/CD  pipeline.  The  power  of this  approach  lies  in  its  consistency. Whether  you  are  deploying  to  the  AWS cloud  utilizing  managed  Dynamo  DB, working  locally  on  a  developer  laptop with  extend  DB  local  or  pushing  to  edge environments  like  an  on-prem  server  rack in  an  airplane.  You  are  utilizing  the exact  same  DynamoB  API.  By  standardizing on  one  data  access  layer,  teams  can leverage  a  single  set  of  operational expertise  across  vastly  different deployment  targets,  significantly reducing  complexity  and  development friction.  To  begin  with  the initialization  flow,  ensure  your environment  meets  the  necessary prerequisites.  You  will  need  a  Linux  or Mac  OS  system,  Rust  version  1.85  or higher,  and  Postgress  version  14  or later.  The  first  step  in  the  process  is to  execute  extend  db  init.  This  command automates  the  setup  by  creating  schemas, generating  certificates  and  admin credentials  and  producing  a configuration  file.  Once  initialized, you  can  create  a  local  development  user with  the  command  extend  db  manage  user create-ame  local  dev.  This  action generates  the  access  key  and  secret  key required  for  authentication. After  generating  your  credentials,  you must  export  them  to  your  environment variables  as  shown  in  the  third  step. Use  the  export  command  to  set  your extend  DB  access  key  ID.  Finally,  you can  verify  the  setup  using  the  AWS  CLI by  specifying  the  endpoint  URL  as  your local  host  on  port  8000.  You  can  run commands  such  as  AWS  DynamoB  list  tables to  confirm  that  the  environment  is  fully operational  and  ready  for  development. The  built-in  management  console  provides a  dedicated  local  web  interface  and  CLI tooling  for  managing  standalone accounts,  users,  and  SIG  v4  credentials. This  system  operates  entirely independently,  allowing  you  to  perform administrative  tasks  without  touching AWS  AM.  The  console  is  organized  into three  primary  modules.  Account administration  which  handles  user profiles  and  organizational  settings. Credential  management  for  the  secure handling  of  keys  and  certificates  and active  connections  which  provides real-time  visibility  into  network traffic  and  connectivity  states.  By hosting  this  interface  locally,  the platform  ensures  a  secure  and streamlined  environment  for  critical management  functions.  This  project  has been  built  in  the  open  and  is  ready  for immediate  experimentation.  You  can  get started  by  cloning  the  repository  to have  a  DynamoB  compatible  endpoint running  locally  in  just  a  few  minutes. We  encourage  active  participation. Please  review  our  contribution  guide  to submit  pull  requests  or  even  build  out new  storage  backends  to  support  broad adoption  and  innovation.  The  project  is released  under  the  Apache  2.0  license developed  by  AWS  engineers.  Further details  and  the  full  announcement  can  be found  on  the  AWS  database  blog.
