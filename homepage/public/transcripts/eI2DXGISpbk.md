Welcome  everyone.  It  is  a  pleasure  to introduce  Badger  DB,  the  Go  Native  key value  store.  Engineered  specifically  for SSDs  and  built  from  the  ground  up  for maximum  performance.  Badger  DB  provides an  embeddible  persistent  storage solution  written  entirely  in  pure  Go.  We designed  it  as  a  highly  performant alternative  to  Rox  DB,  meticulously optimizing  the  engine  to  leverage  the high  throughput  and  parallelism  inherent in  modern  SSD  architecture.  Today, Badger  DB  is  in  a  stable  v4.x  release, already  proving  its  reliability  by powering  pedabyte  scale  data  sets  in demanding  production  environments.  The primary  motivation  for  this architectural  shift  was  Dgraph's  need for  a  storage  engine  that  eliminated  the Seago  bottleneck  without  sacrificing overall  performance.  On  the  right,  we see  the  Sego  friction.  Integrating  C++ stores  like  Rox  DB  introduces significant  build  complexity  and  makes memory  profiling  incredibly  difficult. Most  importantly,  it  creates  scheduler conflicts  between  Go  and  C++  threads represented  here  by  the  tangled  and inefficient  flow  of  execution.  By  moving to  a  pure  Go  architecture,  as  seen  on the  left,  we  gain  native  access  to  Go superior  tooling,  efficient  Go  routine management,  and  fast  compilation  speeds. This  clean  parallel  architecture  allows for  seamless  profiling  with  tools  like Prof,  ensuring  that  the  system  remains both  high  performing  and  maintainable. The  whiskey  thesis  addresses  a  core inefficiency  in  traditional  data  storage by  separating  keys  from  values  to  reduce write  amplification.  In  conventional  log structured  merge  tree  systems  like  Level DB  or  Rox  DB,  both  keys  and  values  are rewritten  together  during  the  compaction process.  This  leads  to  high  right amplification  which  can  significantly degrade  performance  and  shorten  the lifespan  of  flashbased  storage.  Under the  Whiskey  architecture,  incoming  data is  decoupled.  Keys  which  are  small  are maintained  within  an  LSM  tree  in  RAM, allowing  for  instant  iteration  and high-speed  lookups.  Meanwhile,  the values  which  are  typically  much  larger are  appended  sequentially  to  a  dedicated value  log  on  the  SSD  by  only  involving the  keys  in  the  compaction  process.  This design  drastically  reduces  SSD  wear  and leverages  the  devices  superior sequential  write  efficiency.  This approach  famously  implemented  in  Badger DB  provides  a  more  hardware  efficient and  performance  solution  for  modern  high throughput  data  workloads.  This  diagram provides  a  look  under  the  hood  at  how  we optimize  storage  using  a  hybrid  strategy that  combines  an  LSM  tree  with  a  value log.  The  core  objective  here  is  to manage  the  trade-off  between  right performance  and  disk  space  efficiency. In  the  RAM  or  system  memory,  we  maintain an  LSM  tree.  However,  instead  of  storing the  full  data  value  within  the  tree  for every  entry,  we  use  a  selective  approach based  on  data  size.  When  a  new  key  value pair  is  written,  the  system  evaluates the  size  of  the  value  against  a predefined  threshold,  which  defaults  to 4  kilob.  If  the  value  is  smaller  than this  threshold,  it  is  stored  directly within  the  LSM  tree  for  maximum  speed. This  allows  for  fast  lookups  and efficient  caching  of  smaller  frequently accessed  records.  Conversely,  if  the value  exceeds  the  threshold,  as  seen with  larger  blobs  of  data,  we  store  it in  an  appendon  value  log  on  the  SSD  or disk.  In  this  case,  the  LSM  tree  entry consists  of  the  key  and  a  value  pointer or  VPTR,  which  contains  the  file  number and  offset  required  to  locate  the specific  data  in  the  log.  This separation  offers  a  significant performance  advantage  during  background maintenance.  Compactions,  which  are necessary  to  reorganize  and  sort  the data,  only  need  to  process  these lightweight  keys  and  pointers  rather than  the  heavy  data  values  themselves. This  drastically  reduces  the  IO  overhead of  compaction,  ensuring  consistent system  performance  even  as  the  database grows.  Let's  move  to  the  performance benchmarks  for  writes  and  loading. Looking  at  chart  1,  which  measures  data loading  speed,  Badger  DB  shows  a  clear advantage  over  Bolt  DB  and  LMDB, performing  between  1.7  and  22.3  times faster  in  terms  of  throughput.  Turning to  chart  two,  we  see  the  results  for sorted  range  iteration  with  large values.  In  this  scenario,  Badger  DB  is up  to  111  times  faster  than  its competitors.  This  dramatic  increase  in speed  is  largely  due  to  efficient pre-fetching  capabilities.  The  key takeaway  here  is  that  Badger  DB significantly  outperforms  traditional  B+ tree  stores  like  Bolt  and  LMDB.  By design,  it  avoids  random  disc  seeks during  random  writes  and  data  loading, which  allows  it  to  maintain  high performance  where  other  systems typically  encounter  bottlenecks.  Let's examine  the  performance  characteristics regarding  the  read  trade-off  and iteration  speed.  When  performing  random reads,  this  architecture  is  slightly slower,  specifically  about  1.9  times slower  than  LMDB.  This  is  because  a random  read  involves  two  distinct  steps. First,  traversing  the  LSM  tree  in  RAM, and  second,  performing  a  random  IO request  to  fetch  the  data  from  the  value log  on  the  SSD.  In  contrast,  iteration and  range  scans  are  blazingly  fast.  Key only  iterations  stay  entirely  in  RAM, while  full  scans  benefit  from pre-fetching.  This  pre-fetching mechanism  saturates  the  SSD  bandwidth, turning  what  would  be  random  access  into highly  efficient  sequential  throughput. To  optimize  performance,  we  utilize  two key  mitigations.  First,  we  implement Bloom  filters  using  10  bits  per  key. This  probabilistic  filtering  effectively prevents  unnecessary  disc  lookups  for missing  keys.  Second,  we  focus  on  RAM usage,  keeping  the  entire  lightweight LSM  tree  resident  in  memory.  By  ensuring the  index  is  always  in  RAM,  we  minimize the  read  penalty  and  streamline  the  path to  the  physical  data.  Our  approach  to data  integrity  is  built  on  the foundation  of  ACID  transactions  and comprehensive  safety  measures.  We utilize  serializable  snapshot  isolation which  enables  concurrent  ACID transactions  while  ensuring  absolute consistency  even  during  periods  of  high throughput.  To  maintain  these  high standards  of  reliability,  we  implement Jepson  style  verification.  This  involves nightly  bank  tests  that  run  for  eight continuous  hours  with  the  D-Race  flag enabled.  By  simulating  complex concurrent  money  transfers,  we  can rigorously  verify  that  the  system remains  free  from  data  corruption. Lastly,  we  ensure  data  durability through  guaranteed  persistence.  This  is managed  via  a  write-  ahead  log  or  direct value  log  appends  using  syncrites ensuring  that  every  transaction  is securely  recorded  and  permanently stored.  Badger  DB  offers  an  idiomatic  go API  that  focuses  on  being  simple,  native and  free  from  C++  headers.  In  the  first example,  you  can  see  how  a  readm  might transaction  is  performed  using  the update  method.  A  key  advantage  here  is that  closures  handle  the  commit  and discard  logic  automatically  which minimizes  boilerplate  and  prevents common  transactional  errors.  Below  that the  view  method  provides  a  dedicated path  for  readonly  operations.  This creates  a  clear  distinction  between  read write  and  readonly  access  ensuring  that views  are  lock  free  and  highly performant.  This  design  ensures  that interacting  with  the  database  feels natural  and  safe  within  the  Go ecosystem.  Moving  into  advanced features,  we  will  examine  the  stream framework  and  managed  mode.  Both  of which  were  specifically  engineered  for distributed  systems  like  Dgraph.  The stream  framework  provides  a  mechanism for  high  throughput  iteration  which  is essential  for  operations  like  backups and  data  replication.  By  utilizing  go routines,  the  framework  can  process  key value  pairs  concurrently. Separating  keys  from  values provides  significant  performance  gains, but  it  comes  with  the  cost  of  managed garbage  collection.  The  primary challenge  is  that  standard  LSM  tree compactions  only  manage  the  key  value pointers  within  the  LSM  structure.  They do  not  clean  up  the  value  logs themselves.  As  a  result,  invalid  or stale  data  begins  to  accumulate  in  these logs  over  time.  To  address  this,  Badger DB  utilizes  a  specific  garbage collection  mechanism  called  run  value log  GC.  This  process  samples  the  log files  to  identify  candidates  for cleanup,  specifically  those  with  a  high ratio  of  invalid  data,  often  exceeding 50%.  When  such  a  file  is  identified,  the system  moves  all  remaining  valid  entries to  a  new  log  file.  The  original  log  file is  then  deleted,  successfully  reclaiming disk  space  and  ensuring  long-term storage  efficiency.  Badger  in  the  cloud leverages  Kubernetes  for  deployment, specifically  utilizing  stateful  sets  to manage  persistence.  This  configuration involves  a  set  of  pods  labeled  pod  0 through  pod  2  that  maintain  a  stable network  identity  throughout  their  life cycle.  Below  the  compute  layer,  we  have the  persistence  layer  where  each  pod  is mapped  to  its  own  persistent  volume claim.  To  achieve  maximum  IOPS,  these PVCs  are  backed  by  local  NVMe  SSDs  such as  those  found  on  AWS  i3  instances.  A critical  feature  of  this  design  is  its resilience.  If  a  pod  fails,  Kubernetes ensures  that  the  PVC  remounts  to  the replacement  instance  automatically, maintaining  continuous  access  to  the underlying  data.  Now,  let's  examine memory  management  and  the  risks associated  with  the  Linux  OM  killer.  As illustrated  in  the  chart,  there  is  often a  significant  discrepancy  between  actual application  usage  and  the  memory consumed  by  the  page  cache. When  running  Badger DB  in  production,  following  these operational  best  practices  is  essential for  maintaining  stability  and  data integrity.  First,  always  implement  a graceful  shutdown  mechanism.  By correctly  handling  the  SIG  term  signal, you  ensure  the  database  has  enough  time to  flush  its  mem  tables  to  disk  before exiting,  which  prevents  potential  data loss.  Next,  manage  your  lock  files carefully.  Badger  uses  a  lock  file  to ensure  exclusive  access  to  the  data directory.  In  the  event  of  an  unexpected crash,  this  file  may  persist  and  prevent the  database  from  restarting.  We recommend  using  an  init  container  in Kubernetes  to  clear  any  stale  lock  files before  the  main  application  starts.  For maximum  data  safety,  enable  the  sync rights  parameter. This  is  the  safest  setting for  mission  critical  applications  where durability  is  the  top  priority.  Lastly, regarding  infrastructure  management, configure  your  Kubernetes  pods  with  a guaranteed  QoS  class.  By  setting  your resource  requests  and  limits  to  the  same value,  you  protect  your  database  from being  evicted  during  node  resource contention,  ensuring  consistent performance  and  high  availability.
