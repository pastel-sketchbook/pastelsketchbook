They abstract  away  the  complexity  of  managing replica  sets  directly.  Deployments  are the  standard  for  running  production stateless  applications,  including  web APIs  and  microservices,  providing reliability  and  ease  of  updates. While exceeding  the  CPU  limit,  500 milliseconds,  will  result  in  CPU throttling.  Understanding  how  Kubernetes manages  the  health  of  your  applications involves  a  specific  sequence  of specialized  probes. This  cascade  begins  with  the  startup probe,  which  evaluates  first.  Its crucial  role  is  to  disable  both  liveness and  readiness  checks  until  it successfully  passes.  This  prevents slow-starting  applications  from  being prematurely  terminated  before  they've had  a  chance  to  fully  initialize  and become  truly  operational. Once  the  startup  phase  is  complete,  the readiness  probe  takes  over. If  this  probe  fails,  Kubernetes  responds by  removing  the  pod  from  the  service This  action  effectively  stops  client traffic  from  being  directed  to  the unhealthy  pod,  while  critically,  the container  itself  continues  to  run. This  allows  for  potential  self-healing or  debugging  without  disrupting  ongoing operations  for  other  healthy  pods. Finally,  we  have  the  liveness  probe. This  probe  continuously  checks  if  the application  within  the  container  is still  functional  and  responsive.  Should the  liveness  probe  fail,  kubelet  takes  a more  direct  action.  It  kills  the container  and  then  triggers  a  restart based  on  the  defined  restart  policy  for that  particular  workload.  This  ensures that  unresponsive  or  truly  unhealthy containers  are  recycled,  maintaining  the overall  health  and  availability  of  your services.  Understanding  node  maintenance in  Kubernetes  involves  three  key concepts,  which  we've  termed  the  node maintenance  trilogy. This  table  outlines  the  distinct  actions and  impacts  of  cordon,  drain,  and  evict. First,  let's  look  at  cordon,  typically executed  with  kubectl  cordon. Its  primary  action  is  to  mark  a  node  as scheduling  disabled.  This  means  it  does not  affect  any  pods  currently  running  on the  node.  However,  it  does  prevent  any new  pods  from  being  scheduled  onto  that node,  effectively  blocking  new placements.  The  main  use  case  for cordoning  a  node  is  to  temporarily  pause it  and  prepare  it  for  upcoming maintenance,  ensuring  no  new  workloads are  added. Next,  we  have  drain,  invoked  using kubectl  drain.  This  is  a  more comprehensive  operation.  It  first performs  the  cordon  action,  marking  the node  as  scheduling  disabled,  and  then proceeds  to  trigger  the  eviction  of  all existing  pods  from  that  node.  This  is  a graceful  removal  process,  allowing  pods to  terminate  safely.  Because  it  both cordons  and  evicts,  it  affects  both existing  pods  by  removing  them gracefully  and  new  pods  by  blocking their  placement.  Draining  is  commonly used  for  significant  node  operations, like  decommissioning  a  node  entirely  or performing  critical  OS  upgrades,  where the  node  needs  to  be  completely  clear  of Finally,  there's  evict,  which  is fundamentally  an  API  eviction.  This  is an  API  request  designed  to  terminate  a single  pod.  It  directly  affects  existing pods  by  requesting  their  termination. Since  it's  about  individual  pod termination,  the  concept  of  affects  new pods  is  not  applicable.  Eviction  is crucial  because  it  serves  as  the underlying  mechanism  for  a  safe  drain. When  you  run  kubectl  drain,  it internally  initiates  eviction  requests for  each  pod  on  the  node.  The  node maintenance  workflow  details  the  process of  safely  preparing  a  Kubernetes  node for  essential  upkeep.  This  begins  with an  active  node,  which  transitions  to  a cordoned  node  through  the  kubectl  cordon node  command.  Once  a  node  is  cordoned, its  status  becomes  unschedulable, meaning  no  new  pods  will  be  directed  to it  by  the  scheduler. The  next  critical  step  is  to  drain  the node  using  kubectl  drain  node.  This initiates  the  eviction  phase  where Kubernetes  issues  API  eviction  calls  for each  running  pod  on  that  node.  It's crucial  to  note  that  this  process respects  safety  constraints,  ensuring that  pods  are  gracefully  terminated  and if  part  of  a  controller,  rescheduled elsewhere  without  violating  application availability  policies. Finally,  after  all  user  pods  have  been evicted,  the  node  reaches  an  empty  node state.  At  this  point,  the  node  is  safe for  operations  like  a  reboot,  applying an  operating  system  patch,  or  even termination  if  it's  no  longer  needed. For  a  typical  drain  operation,  you  might use  a  command  like  kubectl  drain  node  01 {hyphen}  ignore-daemonsets  {hyphen} The  {hyphen}  ignore-daemonsets  flag prevents  pods  managed  by  daemon  sets from  being  evicted  as  they  are  typically meant  to  run  on  every  node.  The  {hyphen} delete-emptydir-data  flag  ensures  that any  ephemeral  data  stored  in  emptydir volumes  is  also  removed,  making  the  node truly  clean  for  its  next  phase.  The disruption  spectrum  categorizes different  types  of  interruptions  our systems  can  experience.  On  the  left,  we have  voluntary  disruptions  which  are protected.  These  are  planned  events  that allow  for  graceful  handling  of workloads.  Examples  include  running kubectl  drain  for  maintenance  where  pods are  safely  evicted,  the  cluster  auto scaler  removing  underutilized  nodes  to optimize  resources,  upgrading  node operating  systems  or  kubelet  binaries, and  custom  controllers  replacing  worker nodes  as  part  of  a  managed  process. These  actions  are  typically  handled  with mechanisms  like  pod  disruption  budgets to  ensure  application  availability. Conversely,  on  the  right,  we  encounter involuntary  disruptions  which  are  not protected.  These  are  unexpected  and often  lead  to  abrupt  termination  of workloads.  Common  examples  include hardware  failures  such  as  a  disk  crash or  a  kernel  panic,  an  underlying hypervisor  or  virtual  machine  crashing, network  partitions  or  cable  disconnects, and  a  node  running  out  of  physical memory,  triggering  an  out-of-memory  OOM panic.  Unlike  voluntary  disruptions, these  events  offer  no  opportunity  for graceful  termination,  making  resilience against  them  a  critical  design consideration.  Guarding  your  workloads effectively  with  pod  disruption  budgets is  paramount  for  maintaining  service availability  during  planned  events.  A pod  disruption  budget,  or  PDB,  serves  as an  API  level  safety  gate  designed  to rate  limit  simultaneous  pod  evictions that  occur  during  voluntary  disruptions, such  as  when  you  perform  a  kube-cuddle drain  on  a  node.  We  have  two  primary configurations  for  defining  a  PDB.  The first  is  min  available,  which  specifies the  minimum  number  of  pods  that  must remain  running  and  healthy  at  all  times. This  configuration  is  particularly useful  for  quorum-based  applications like  Kafka,  Zookeeper,  or  etcd,  which require  a  strict  minimum  quorum,  for example,  two  out  of  three  instances,  to function  correctly.  The  second configuration  is  max  unavailable.  This setting  defines  the  maximum  number  of pods  that  are  permitted  to  be  down simultaneously.  It's  typical  use  case  is for  stateless  APIs  or  websites,  where the  architecture  can  tolerate  a  certain percentage  of  pods  being  temporarily unavailable  without  significant  service A  crucial  rule  to  remember  when  defining your  PDB  is  that  you  can  specify  values for  either  min  available  or  max unavailable  using  an  absolute  number  or a  percentage.  However,  it's  essential not  to  include  both  min  available  and max  unavailable  within  the  same  manifest file.  Examining  the  anatomy  of  a  pod disruption  budget,  we  see  a  YAML configuration  that  defines  how  many disruptions  an  application  can  tolerate. This  specific  example,  named  API  PDB, sets  a  min  available  of  80%.  This percentage  translates  directly  to  the guarantee  that  for  a  five-replica deployment,  at  least  four  replicas  will remain  active  and  healthy,  even  during  a node  drain. The  selector  section,  particularly  the match  labels,  is  a  critical  component here.  It  links  this  disruption  budget  to the  specific  pods  it  is  meant  to protect.  If  these  labels  do  not perfectly  match  the  labels  defined  in the  associated  deployment,  the  pod disruption  budget  will  effectively ignore  those  pods.  Consequently,  any node  drain  operation  would  evict  all  of them  simultaneously  without  any  rate limiting  or  adherence  to  the  budget, potentially  leading  to  significant downtime.  The  eviction  API  gatekeeper plays  a  crucial  role  in  maintaining application  availability  during  node maintenance.  This  diagram  illustrates the  process  initiated  by  a  kubectl  drain node  zero  one  command.  The  drain  command first  requests  an  eviction  via  the {slash}  eviction  API  endpoint.  The Kubernetes  API  server  then  acts  as  the gatekeeper,  evaluating  matching  pod disruption  budget,  or  PDB,  rules  against the  current  cluster  replica  counts. If  the  budget  is  available,  meaning evicting  the  pod  will  not  violate  any PDBs,  the  eviction  is  approved.  This leads  to  a  graceful  pod  deletion,  the replica  set  automatically  creating  a replacement  pod,  and  importantly, traffic  remaining  unaffected.  However, if  the  budget  is  exceeded,  the  eviction is  rejected  with  an  HTTP  429  too  many requests  status.  In  this  scenario,  the kubectl  drain  command  pauses,  logs  a warning,  and  continuously  retries  the eviction  request  until  new  replacement pods  are  ready  and  the  PDB  rules  can  be This  mechanism  ensures  that  critical application  availability  is  maintained even  during  planned  node  disruptions. At  the  top,  we observe  the  workload  layer,  comprised  of a  deployment  managing  a  replica  set, which  in  turn  orchestrates  three  pods. Initially,  one  pod  resides  on  node  A, while  the  other  two  are  active  on  node B,  representing  our  compute infrastructure.  The  depicted  scenario focuses  on  a  cube  CTL  drain  operation being  initiated  on  node  A,  indicating planned  maintenance  or  an  upgrade. The  PDB  ledger  serves  as  a  vital safeguard,  continuously  measuring  the health  and  availability  of  the  replica set. As  the accompanying  text  emphasizes,  achieving zero  downtime  operations  necessitates  a complete  chain  of  trust.  A  node  drain triggers  this  eviction  API  call,  which then  relies  on  the  PDB  ledger  to  verify the  replica  set's  health,  all  under  the orchestration  of  the  deployment.  Should any  link  in  this  chain  fail,  for instance,  if  the  PDB  determines  that  an eviction  would  compromise  the  workload's minimum  availability,  the  system  halts the  operation,  thereby  protecting  the workload  from  disruption  and  ensuring its  high  availability.  A  common  issue encountered  during  Kubernetes  node drains  is  a  hang,  often  indicated  by  the API  server  returning  an  HTTP  429  too many  requests  status. This  occurs  because  evicting  the  target pod  would  cause  the  number  of  healthy replicas  to  fall  below  the  pod disruption  budget's  minimum  threshold. As  we  see  in  the  cube  CTL  get  PDB  output for  my  app  PDB,  while  there  are  3  ready pods  and  a  minimum  of  two  are  required, the  allowed  disruptions  value  is  zero. This  means  that  even  though  the  workload technically  could  tolerate  losing  one pod  and  still  meet  min  available  two, the  PDB  explicitly  forbids  any disruption.  These  drain  hangs  typically stem  from  several  common  pitfalls. First,  unready  replacements  occur  when nodes  lack  sufficient  CPU  or  RAM, preventing  new  pods  from  starting,  or when  new  pods  fail  their  readiness probes,  meaning  they  are  never considered  healthy  enough  to  replace existing  ones.  Second,  single  replica workloads  are  highly  susceptible.  If  a deployment  has  only  one  replica  and  its min  available  is  set  to  one,  losing  that single  pod  drops  the  available  count  to zero,  creating  a  permanent  block. Finally,  a  100%  availability requirement,  where  min  available  is  set to  100%,  effectively  allows  zero disruptions  ever,  regardless  of  the number  of  replicas,  making  it  impossible to  perform  controlled  evictions.  These resolution  strategies  illustrate  a progression  from  the  safest,  most standard  approaches  to  increasingly forceful  methods  for  managing  Kubernetes pods  and  nodes. Our  first  option,  labeled  tier  one,  is option  A,  fix  replacements,  which  is both  the  safest  and  the  standard practice.  This  involves  addressing  the underlying  cluster  state,  such  as  adding node  capacity  or  fixing  taints,  to ensure  that  replacement  pods  can successfully  pass  their  readiness Alternatively,  for  a  temporary  solution, you  can  scale  up  a  deployment  using kubectl  scale  deployment  space  name  * replicas  =  +1. Moving  to  tier  two,  we  have  option  B, temporarily  delete  PDB,  or  a  controlled This  strategy  is  suitable  for  planned maintenance  scenarios,  where  you  can temporarily  accept  a  degraded The  command  is  kubectl  delete  PDB  space name,  and  it's  crucial  to  remember  to reapply  the  PDB  manifest  after  the maintenance  is  complete  to  restore Tier  three  presents  a  more  aggressive approach,  option  C,  bypass  eviction  API, which  is  a  forceful  action. This  method  skips  pod  disruption  budget verification  across  the  entire  node.  A significant  warning  accompanies  this option.  It  may  potentially  take  down quorum  critical  services.  The  associated command  is  cube  cuddle  drain  space  node times  disable  eviction. Finally,  at  tier  four,  the  most  direct and  forceful  option  is  option  D, manually  delete  target  pod,  considered  a surgical  override. This  involves  making  a  standard  delete call  directly  to  the  pod  deletion  API, effectively  bypassing  any  pod  disruption budget  or  eviction  endpoint  enforcement. The  command  for  this  is  cube  cuddle delete  pod  space  name.
