Welcome  everyone.  Today  I  am  excited  to introduce  you  to  Jiujutsu  or  JJ,  a project  that  represents  a  Git  compatible revolution  in  version  control.  While  Git fundamentally  changed  how  we  store  and manage  code,  its  interface  has  remained rooted  in  low-level  implementation details  for  decades.  Jujutsu  reimagines this  experience  from  the  ground  up.  It offers  fearless  version  control  by treating  conflicts  as  first  class citizens  and  eliminates  the  friction  of the  traditional  staging  area.  By  using Git  as  a  robust  storage  backend  while completely  redesigning  the  user interface,  Jiujutsu  prioritizes  the human  mental  model  over  the  underlying database  schema,  allowing  developers  to focus  on  their  work  rather  than  the complexities  of  their  tools.  Git  is  a powerful  tool,  but  it  imposes  a significant  hidden  tax  on  developer productivity  through  its  complex underlying  mechanics.  First,  let's  look at  the  staging  area,  also  known  as  the index.  This  acts  as  a  manual  holding zone  that  demands  constant  mental overhead.  Rather  than  allowing developers  to  focus  on  logical  changes, it  forces  them  to  micromanage  file states,  often  leading  to  cumbersome command  sequences  just  to  organize  work in  progress  code.  Second,  we  face  stop the  world  conflicts  in  Git.  A  merge conflict  effectively  halts  your  entire workflow.  It  creates  a  rigid  state  where you  cannot  easily  switch  branches  or save  your  current  context  until  the conflict  is  fully  resolved,  causing significant  friction  during collaborative  development.  Finally, there  is  the  issue  of  brittle  history. While  interactive  rebasing  is  often  used to  keep  a  history  clean,  it  is fundamentally  dangerous.  Modifying  an existing  commit  changes  its  unique  Shaw identity,  which  can  break  the  commit graph  for  the  rest  of  the  team.  These three  factors  illustrate  how  the standard  Git  workflow  can  prioritize system  architecture  over  developer velocity.  This  slide  introduces  a  new approach  to  interacting  with  the  Git database  through  Jiujutsu  or  JJ.  At  the top  level,  we  have  the  JuiJutsu interface,  a  Rustbased  CLI  that  focuses on  the  what  of  your  workflow  by abstracting  away  the  how  of  the underlying  storage.  It  communicates through  a  storage  API  with  the  git storage  backend.  Because  this  backend consists  of  standard  Git  repositories, it  maintains  full  compatibility  with GitHub,  GitLab,  and  existing  CI  tools. By  separating  the  user  interface  from the  storage  layer,  Juju  ensures  that  to any  server  or  collaborator,  your  code appears  as  normal  Git  commits.  This allows  you  to  adopt  the  power  and features  of  a  next  generation  version control  system  without  requiring  your team  or  infrastructure  to  migrate  away from  the  Git  ecosystem.  The  first paradigm  shift  we  are  exploring  is  the concept  that  the  working  copy  is  itself a  commit.  In  traditional  version control,  your  uncommitted  changes  exist in  an  intermediate  state.  But  here  the working  copy  designated  by  the  at  symbol is  a  functional  part  of  the  commit graph.  This  structure  allows  for automatic  snapshotting.  Every modification  is  recorded  to  the  at commit  instantly  removing  the  need  for manual  commands  like  git  add  or  git stash.  You  no  longer  have  to  worry  about manually  saving  your  progress.  The system  does  it  for  you.  This  shift  also brings  a  sense  of  uniformity  to  your workflow  because  your  inprogress  work  is treated  as  a  standard  commit.  The  same operations  used  for  managing  history such  as  diffing,  rebasing,  and  squashing can  be  applied  directly  to  your  current working  copy.  Lastly,  this  model provides  inherent  safety.  you  are  always working  within  a  commit  which  eliminates the  limbo  state  where  files  are  neither fully  tracked  nor  committed.  This ensures  that  your  work  is  always captured  within  the  version  control structure  leading  to  a  more  stable  and reliable  development  experience.  Let's examine  the  second  paradigm  shift  the distinction  between  a  change  ID  and  a commit  ID.  In  Git,  we  operate  with  what is  known  as  a  brittle  identity.  Whenever you  amend  content,  the  Shaw  hash changes,  moving  from  A1B2  to  C3D4.  In this  example,  because  the  hash  is  the primary  identifier,  the  logical  identity of  the  work  is  lost  during  the modification  process.  Jiujitsu,  by contrast,  provides  a  stable  identity.  It separates  the  logical  unit  of  work  from the  specific  file  snapshot.  Notice  how the  change  ID  YZ  and  K  remains  constant even  as  the  content  evolves  and  a  new commit  hash  is  produced.  By  tracking  the logical  change  unit  rather  than  just  the snapshot,  Juju  allows  you  to  rewrite history  and  rebase  frequently  without ever  losing  track  of  the  underlying  work unit.  Moving  on  to  paradigm  shift  number three,  we  introduce  the  concept  of  first class  conflicts.  In  traditional  version control  systems,  a  merge  conflict  is often  treated  as  a  workflow  error,  a barrier  that  halts  progress  until  it  is manually  resolved.  Under  this  new paradigm,  we  treat  conflicts  as  data.  As illustrated  in  the  diagram,  a  conflict is  recorded  directly  within  a  commit, allowing  it  to  exist  as  a  valid,  albeit unresolved  state  in  the  repositories history.  This  shift  offers  several  key advantages.  First,  it  is  non-blocking.  A conflict  no  longer  stops  the  world.  You can  commit  a  file  containing  conflict markers,  switch  to  a  different  task,  and return  to  resolve  it  later.  Second,  we leverage  algebraic  merging.  Since conflicts  are  stored  within  the  commit, rebased  resolutions  can  mathematically simplify  the  version  tree,  leading  to  a more  streamlined  and  predictable history.  Finally,  this  model  enhances collaboration.  Because  a  conflicted state  is  simply  data,  you  can  push  it  to the  server  and  ask  a  colleague  for assistance,  transforming  a  technical hurdle  into  a  collaborative  opportunity. The  operation  log  is  the  foundation  of fearless  experimentation  in  Jiujutsu. While  Git  users  might  be  familiar  with the  ref  log,  it  is  often  ephemeral  and difficult  to  manage.  Juju  takes  this concept  further  with  a  permanent operation  log  that  enables  true  time travel.  Every  action  from  commits  and navigation  to  complex  rebases  is recorded.  This  allows  for  instant recovery  through  the  JJ  undo  command which  reverts  the  repository  state  to exactly  how  it  was  before  your  last operation.  The  ultimate  takeaway  is  that you  cannot  break  your  repo.  You  are  free to  experiment  with  history  rewriting  and complex  maneuvers  without  any  of  the usual  anxiety.  Anonymous  branching  is designed  to  protect  your  flow  state  by removing  the  cognitive  overhead  of naming  every  temporary  idea.  In traditional  version  control,  creating  a new  branch  often  requires  you  to  stop and  think  of  a  descriptive  name  before you  can  even  begin  coding.  With jiu-jitsu,  branches  are  anonymous  by default.  You  can  simply  run  JJ  new  to start  a  new  line  of  work  without  the friction  of  inventing  names  like  fix  bug attempt  2  or  experimental  refactor. Ultimately, Juju  reduces  command  friction  and  the mental  overhead  of  state  management, allowing  you  to  focus  more  on development  and  less  on  the  version control  tool  itself. If  you  need  to  modify  a parent  branch,  you  are  forced  to manually  rebase  every  descendant  branch which  is  timeconuming  and  errorprone. Jiujitsu  or  JJ  eliminates  this  friction with  its  autorebase  functionality.  When you  modify  a  parent  commit,  JJ automatically  rebases  all  descendant features  for  you.  This  ensures  stability throughout  the  stack  using  change  IDs, allowing  you  to  focus  on  development rather  than  branch  maintenance.
