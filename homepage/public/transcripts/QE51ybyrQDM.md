Welcome.  Today  we  are  going  to  explore the  core  principles  behind  designing  the eventdriven  landscape.  This  presentation serves  as  a  conceptual  blueprint  for navigating  the  complexities  of  modern messaging  patterns,  protocol  standards, and  the  implementation  of  cloud  events. As  we  examine  the  interconnected  map before  us,  we  will  discuss  how  to  build resilient,  scalable  architectures  that effectively  orchestrate  data  and  events across  diverse  environments.  In  the architecture  of  distributed  systems, communication  falls  into  two  distinct philosophical  categories.  The  intent versus  fact  divide.  On  the  left,  we  have commands  and  jobs.  These  represent  a specific  intent  or  expectation  to  be fulfilled.  In  this  paradigm,  one  message is  sent  to  one  intended  receiver  acting as  a  transfer  of  control.  It  is  an explicit  instruction  to  do  this.  On  the right,  we  have  events.  These  represent facts  and  serve  as  an  immutable  record of  history.  Unlike  a  command,  a  single event  can  have  zero  to  many  receivers. This  represents  a  transfer  of  value, broadcasting  to  the  system  that  this happened.  Distinguishing  between  the directive  of  a  command  and  the historical  truth  of  an  event  is essential  for  building  robust  and decoupled  distributed  architectures. This  slide  illustrates  the  process  of deriving  actionable  signals  from  raw observations.  On  the  graph,  we  see continuous  streams  of  data  representing environmental  observations  such  as temperature  and  humidity  tracked  over time.  While  these  individual  data  points provide  a  baseline,  their  primary utility  comes  from  the  derivative signals  we  compute  from  sequences  of these  observations.  As  shown  here,  the system  continuously  monitors  the  trend of  these  inputs.  When  a  combination  of factors  or  a  specific  pattern  crosses  a predefined  average  threshold  marked  by the  dashed  horizontal  line,  a  derivative signal  is  instantly  generated.  In  this specific  scenario,  that  signal  is  a  fire alarm  represented  by  the  green  vertical spike.  These  derivative  signals  are crucial  because  they  transform  complex raw  data  into  immediate  actionable insights  that  require  an  urgent response.  Defining  the  bounded  context is  essential  to  understanding  how  domain driven  design  operates  within  a microservices  architecture.  As  noted, the  exact  same  term  can  possess  entirely different  meanings  depending  on  its relation  to  a  service  boundary.  To manage  this  distinction  effectively,  we categorize  events  as  either  inside  or outside.  Inside  events  are  used  strictly for  internal  service  logic.  These  events remain  within  the  services  private boundary  and  are  highly  coupled  to internal  domain  models.  This  coupling allows  for  internal  flexibility  and rapid  change  without  impacting  external systems.  Outside  events,  on  the  other hand,  are  utilized  for  cross  service communication.  Because  these  events cross  the  service  boundary,  they function  as  public  contracts.  This necessitates  the  use  of  schema registries  such  as  an  event  catalog  and demands  comprehensive  business  level documentation  to  ensure  that  all consuming  services  maintain  a  consistent understanding  of  the  shared  data. Standardized  naming  conventions  are essential  because  they  immediately signal  the  intent  of  a  payload  to  its consumers,  ensuring  clarity  and consistency  across  the  system.  We  use three  primary  formulas  depending  on  the events  purpose.  First  for  notification and  delta  events  which  communicate simple  state  changes.  The  formula  is  a noun  followed  by  a  past  tense  verb.  For example,  order  created  clearly  denotes that  a  specific  action  has  occurred. Second,  we  have  fact  events  which  are used  for  event  carried  state  transfers to  communicate  the  full  state  of  an entity.  The  convention  here  is  to  append fact  to  the  event  name  resulting  in identifiers  like  order  created  fact. Finally,  for  inside  domain  events  that are  namespaced  for  internal  bounded contexts,  we  use  the  namespace  followed by  an  at  symbol  and  the  event  name.  An example  of  this  is  order  at  order created  which  provides  explicit  context for  consumers  operating  within  that specific  domain.  This  slide  outlines onetoone  communication  topologies  which define  direct  routing  paths  between  a singular  source  and  target.  We  can categorize  these  interactions  into  four primary  patterns.  In  a  push  topology, the  source  proactively  initiates  the transfer  of  data  or  instructions directly  to  the  target.  Conversely,  in  a pull  topology,  the  target  acts  as  the initiator,  requesting  and  retrieving data  from  the  source  as  needed.  The brokered  model  introduces  an intermediary  such  as  a  message  cue  to decouple  the  communication  between  the source  and  target.  The  source  sends  its message  to  the  intermediary  which  then manages  the  delivery  to  the  target enabling  asynchronous  workflows. Finally,  the  request  response  or  RPC model  represents  a  synchronous  cycle. The  source  sends  a  request  through  an intermediary  to  the  target  and  once  the task  is  processed,  the  target  sends  a response  directly  back  to  the  source. Each  of  these  topologies  serves  specific architectural  needs  regarding  timing, decoupling,  and  flow  control.  One  to event  distribution  topologies  represent routing  patterns  designed  to  dispersing facts  to  multiple  downstream  consumers. There  are  three  fundamental  models utilized  to  manage  this  data  flow. First,  the  broadcast  pattern  is  used  to reach  everyone.  The  source  sends  an event  to  an  intermediary  which  then distributes  it  to  every  single  target  in the  system.  This  ensures  that information  is  universally  available  to all  nodes  simultaneously. Second  is  multiccast  which  functions  on a  conditional  basis.  Here  the intermediary  filters  the  distribution  so that  only  a  select  subset  of  targets receives  the  event.  This  targeted approach  is  based  on  specific  criteria or  subscriptions  allowing  for  efficient communication  within  a  large  network. Finally,  anycast  is  designed  to  reach one  of  the  eligible  consumers.  In  this topology,  although  multiple  targets  are available,  the  intermediary  routes  the event  to  exactly  one  recipient.  This  is typically  determined  by  proximity  or current  load  making  it  a  critical pattern  for  load  balancing  and  service discovery. Symmetry, multipplexing,  and  primary  communication patterns.  Starting  with  HTTP  1.1,  we  see a  traditional  client  initiated  model.  It lacks  both  native  symmetry  and multipplexing  capabilities,  focusing primarily  on  the  request  response pattern  commonly  associated  with  restful services.  Moving  to  websockets,  while the  initiation  remains  non-ymmetric,  we gain  the  advantage  of  multipplexing through  stream  tunneling.  This  enables its  primary  pattern  of  a  persistent birectional  stream,  which  is  ideal  for real-time  data  exchange.  Finally,  MQTT represents  a  highly  flexible  option within  this  comparison.  It  is  inherently symmetric  and  supports  multiplexing, facilitating  a  primary  publish  subscribe pattern.  This  architecture  makes  MQTT exceptionally  efficient  for  resource constraint  environments  due  to  its minimal  wire  overhead.  To  understand  how data  travels  across  a  network,  we  must examine  the  nested  layers  of  metadata that  wrap  raw  payload  data  for  wire transit  and  protocol  parsing.  At  the very  center  of  this  model  is  the  payload which  represents  the  actual  event  data being  transmitted.  Immediately surrounding  this  core  is  the  payload metadata  providing  essential  information about  the  data  structure  such  as  its size  and  encoding  language.  Moving outward  we  find  application  metadata which  contains  specific  instructions intended  for  the  receiving  application. It  is  important  to  note  that  not  all protocols  allow  for  separate  application metadata,  sometimes  requiring  external conventions  to  facilitate  these instructions.  Finally,  the  outermost layer  is  the  protocol  metadata.  This layer  is  critical  for  network functionality,  containing  the information  required  for  the  protocol  to function,  specifically  for  routing  the data  to  its  destination.  Transfer asurances  are  essential  strategies designed  to  compensate  for  data  loss, prevent  duplication,  and  maintain  proper sequencing  when  communicating  over unreliable  connections.  There  are  three primary  levels  of  assurance  to  consider. First,  we  have  at  most  once,  often referred  to  as  best  effort  delivery.  In this  model,  the  mechanism  is straightforward.  The  sender  makes  a single  attempt  to  transmit  data  and  does not  resend  the  frame  even  if  an acknowledgement  is  missing.  As illustrated,  if  a  frame  is  lost  during transit,  no  further  attempt  is  made  to deliver  it.  While  this  approach  offers the  lowest  latency  and  overhead,  it provides  no  guarantee  that  the information  will  actually  reach  the receiver.  Second  is  the  at  least  once strategy.  Here  the  mechanism  ensures that  a  frame  is  resent  continuously until  an  acknowledgement  from  the receiver  proves  successful  delivery. This  approach  guarantees  that  no  data  is permanently  lost.  However,  it  introduces the  risk  of  potential  duplication.  If  a message  is  delivered  but  the acknowledgement  fails  to  reach  the sender,  the  sender  will  transmit  the data  again  resulting  in  multiple  copies of  the  same  frame  at  the  destination. Finally,  exactly  once  delivery represents  the  most  robust  but  resource inensive  approach.  It  carries  the highest  overhead  because  it  requires sophisticated  tracking  to  guarantee  a single  ordered  delivery  for  every  frame. By  effectively  managing  acknowledgements and  identifying  duplicates,  this strategy  ensures  that  each  message  is processed  exactly  one  time  and  in  the correct  sequence,  providing  the  highest level  of  reliability  for  critical  data transfers.  Untangling  the  wire  involves four  key  stages  to  transform  raw  data into  usable  information.  First,  we  have the  stream,  which  is  a  continuous undifferentiated  flow  of  binary  data. Without  structure,  this  data  is impossible  for  a  system  to  interpret efficiently.  To  address  this,  we  move  to the  second  stage,  framing.  Here,  the protocol  splits  the  stream  into  distinct bounded  chunks,  effectively  marking  the start  and  end  of  individual  messages. Third  is  data  layout.  Each  frame  chunk is  organized  into  two  primary  sections, a  frame  header  and  a  frame  body.  The header  provides  vital  metadata, including  the  packet  size  and destination,  ensuring  the  system  knows exactly  how  much  data  to  read  and  where it  should  go.  Finally,  the  encoding stage  defines  how  the  information  within the  frame  body  is  serialized.  By  using protocols  like  JSON,  AVO,  Protobuff  or CSV,  we  ensure  that  the  data  is structured  in  a  format  that  the receiving  application  can  readily  parse and  process.  The  cloud  event  standard  is a  vendorneutral  lightweight  convention for  events,  intentionally  omitting routing  complexity  to  strictly  describe facts.  Central  to  the  standard  is  the envelope  which  provides  a  consistent structure  for  event  metadata. Type  systems  and  system constraints  are  fundamental  to  ensuring that  cloud  events  can  move  seamlessly across  diverse  environments. Cloud  events  defines  three structural  paradigms  for  transferring event  metadata  alongside  the  payload. Structured,  binary,  and  batched  modes. These  modes  determine  how  event information  is  mapped  onto  a  transport protocol.  In  structured  mode,  both  the event  metadata  and  the  event  data  are combined  into  a  single  payload, typically  formatted  as  a  JSON  object. This  approach  ensures  the  entire  event is  self-contained  within  the  message body,  making  it  easy  to  store  or  pass through  various  systems  without  losing context.  Binary  mode  takes  a  different approach  by  mapping  the  event  metadata directly  into  transport  headers  such  as HTTP  headers.  The  message  body  is reserved  strictly  for  the  event  data. This  mode  is  highly  efficient  for performance-sensitive  applications  as  it allows  middleware  to  route  or  filter events  based  on  headers  without  needing to  parse  the  entire  payload.  Finally, batched  mode  allows  for  multiple  events to  be  grouped  together  within  a  single transport  envelope  body.
