# The Architecture of Modern Identity

Welcome  everyone.  Today  we  are  diving into  the  complex  and  fascinating  world of  digital  access  as  we  explore  the architecture  of  modern  identity.  Over the  course  of  this  session  we  will examine  how  fundamental  protocols  like Keraros,  SAML,  Oath  2,  OIDC  and  SKIM integrate  to  form  a  cohesive  framework. Our  focus  will  be  on  understanding  how these  individual  components  build  a secure  seamless  enterprise  ecosystem that  balances  robust  security  with  a frictionless  user  experience.  Let's begin  by  looking  at  how  these  pieces  fit together  to  protect  and  enable  the modern  digital  landscape.  This architectural  model  illustrates  a comprehensive  multi-layered  approach  to identity  management  and  security protocols.  At  the  base,  layer  1  serves as  the  internal  foundation,  utilizing Keraros  to  secure  local  workstations  and the  internal  network.  Moving  up,  layer  2 functions  as  the  cloud  bridge, leveraging  SAML  and  OIDC  protocols  to extend  single  signon  capabilities  to  web and  enterprise  applications.  Layer  3 focuses  on  API  security  where  OOTH  2  is implemented  to  secure  back-end  data access  and  manage  micros  service traffic.  Encompassing  the  entire structure  is  the  background  layer  for life  cycle  automation.  This  layer employs  SKIM  to  handle  the  automated provisioning  and  deprovisioning  of  user identities  in  the  background.  Together these  layers  ensure  a  robust  and seamless  security  framework  across  the entire  organizational  ecosystem.  Keraros serves  as  the  internal  foundation  for secure  network  authentication.  It  is  a ticket-based  protocol  that  utilizes symmetric  key  cryptography  to  verify identities  without  ever  transmitting passwords  across  the  network.  The process  is  illustrated  in  three  main stages.  It  begins  at  the  client workstation  which  initiates  the authentication  flow.  This  request  is sent  to  the  key  distribution  center  or KDC  which  functions  as  the  central authority  to  issue  a  ticket  granting ticket  or  TGT.  Once  obtained,  this ticket  allows  the  user  to  request  access to  local  resources  which  then  validate the  service  tickets  to  provide  secure access  to  the  network's  assets.  This protocol  is  best  for  highsecurity on-prem  environments,  Windows  Active Directory,  local  fileshares,  and  thick clients  located  inside  the  firewall. SAML  or  security  assertion  markup language  serves  as  a  robust  XML-based bridge  for  identity  management  in  the cloud.  It  is  an  open  standard  designed to  exchange  authentication  and authorization  data  between  an  identity provider  known  as  the  IDP  and  a  service provider  or  SP.  This  mechanism  is  the foundation  for  enabling  single  signon across  various  platforms.  The  process follows  a  specific  five-step  flow. First,  a  user  attempts  to  access  an application  through  their  browser.  Since the  user  is  not  yet  authenticated,  the service  provider  redirects  the  browser to  the  identity  provider  in  step  two.  In the  third  step,  the  user  authenticates directly  with  the  IDP,  typically  by entering  their  credentials.  Once  the user's  identity  is  verified,  step  four involves  the  IDP  sending  a  signed  XML assertion  back  to  the  service  provider via  the  user's  browser.  Finally,  in  step five,  the  service  provider  validates this  assertion  and  grants  the  user access  to  the  requested  application. SAML  is  considered  the  heavyweight option  because  of  its  extensive  security features  and  widespread  adoption.  It  is best  suited  for  legacy  enterprise  web applications  like  Salesforce  or  Workday as  well  as  for  facilitating  B2B partnerships  and  federated  identity management  across  different organizations. OOTH  2  is  an  authorization  framework designed  specifically  for  delegated authorization  which  is  a  distinct concept  from  authentication.  Its  primary function  is  to  issue  limited  timebound access  tokens  allowing  a  client application  to  access  specific  resources on  a  user's  behalf  without  ever  seeing or  sharing  that  user's  password.  As shown  in  the  diagram,  the  client  app utilizes  an  access  token  comparable  to  a valet  key  to  communicate  with  the resource  server.  This  workflow  typically involves  three  steps.  First,  the  user approves  specific  scopes  at  the authorization  server.  Second,  an authorization  code  is  exchanged  for tokens.  Third,  those  tokens  are  used  to securely  call  backend  APIs.  This approach  is  best  suited  for  thirdparty integrations  such  as  a  photo  app accessing  cloud  storage  as  well  as secure  mobileto  backend  communication and  server  to  server  traffic.  Open  ID connect  or  OIDC  is  fundamentally  about knowing  who  the  user  is.  Built  directly on  top  of  the  OOTH2  authorization framework.  It  serves  as  the  modern standard  for  single  signon.  While  OOTH  2 handles  authorization,  OIDC  adds  a dedicated  identity  layer  by  introducing an  ID  token.  This  is  a  signed  JSON  web token  that  contains  specific  user  claims such  as  their  name  and  email  address. Essentially,  OIDC  is  an  upgrade  that reuses  established  OAF2  flows,  but incorporates  the  open  ID  scope  to  verify identity  alongside  access  permissions. This  approach  is  ideal  for  modern  web and  mobile  SSO  environments,  single  page applications,  and  consumer  federated authentication,  the  common  signin  with Apple  or  sign-in  with  Google  experiences we  see  today.  SIM  is  a  REST  and JSONbased  standard  specifically  designed to  automate  the  account  life  cycle.  It focuses  on  the  automated  provisioning and  deprovisioning  of  users  and  groups. It  is  important  to  note  that  while  SIM manages  identity  information,  it  is  not an  authentication  protocol.  Looking  at the  flow  in  this  diagram,  the  HR  system serves  as  the  source  of  truth  for identity  data.  SIM  functions  as  the engine  that  performs  CRUD  operations, create,  read,  update,  and  delete  over HTTP.  This  allows  for  the  birectional synchronization  of  identity  data  between the  HR  system,  the  identity  provider, and  various  cloud  applications  like Slack  and  Salesforce.  This  approach  is best  suited  for  just  in  time  user onboarding,  continuous  directory synchronization,  and  the  immediate revocation  of  access.  By  automating these  processes,  organizations  can ensure  seamless  transitions  for employees  while  maintaining  strict security  compliance.  To  understand  the anatomy  of  a  session  and  how  various security  protocols  interoperate,  we  can trace  the  journey  of  an  employee  from their  initial  onboarding  to  active  daily tasks.  It  begins  with  background  prep using  SIM  or  system  for  cross-domain identity  management.  When  an  employee  is hired,  SIM  ensures  their  account  is automatically  provisioned  across  all necessary  platforms,  establishing  a consistent  identity  foundation.  Next,  we move  to  step  one,  local  login.  Using Keraros,  the  employee  logs  into  their Windows  laptop.  This  protocol  secures the  local  session  by  verifying  identity without  the  need  to  transmit  actual passwords  across  the  network,  reducing the  attack  surface.  In  step  two,  we transition  to  cloud  access  via  SAML  or OIDC.  When  the  employee  opens  a  web browser  to  access  the  corporate dashboard,  these  single  signon  protocols leverage  the  existing  authenticated session  to  log  them  in  automatically. This  provides  a  seamless  user  experience between  the  local  hardware  and cloud-based  resources.  Finally,  step three  involves  the  data  fetch  using  OOTH 2.  Once  the  user  is  inside  the dashboard,  OOTH  2  enables  the application  to  securely  retrieve  the user's  customized  data  from  separate back-end  microservices.  By  combining SIM,  Kerarose,  SAML,  and  OOTH  2, organizations  can  create  a  secure interoperable  ecosystem  that  balances robust  security  with  user  productivity. The  protocol  selection  matrix  provides  a framework  for  choosing  the  correct identity  standard  based  on  specific architectural  needs.  First,  Keraros  is designed  for  internal  authentication within  a  corporate  network.  It  operates using  tickets  and  can  be  thought  of  as  a set  of  local  keys.  This  remains  the standard  for  on  premises  environments, particularly  those  integrated  with active  directory.  Second,  SAML  is  the foundation  for  web-based  single  signon. Utilizing  an  XML  data  format,  it functions  as  a  B2B  passport  for enterprise  users.  It  is  the  ideal  choice for  integrating  heavyweight  SAS applications  such  as  workday  into  your identity  ecosystem.  Third,  OOTH  2  is focused  specifically  on  API authorization.  It  issues  access  tokens that  act  as  a  valet  key  providing restricted  access  to  resources  without sharing  master  credentials.  This  makes it  the  preferred  protocol  for  securing APIs  and  facilitating  machineto-achine communication.  Fourth,  OIDC  or  Open  ID Connect  is  a  modern  authentication  layer built  on  top  of  OOTH  2.  It  uses  JSON  web tokens  to  serve  as  a  digital  ID  badge that  proves  a  user's  identity.  This  is the  standard  for  modern  single  page applications  and  mobile  apps.  Finally, SKIM  handles  the  account  life  cycle  by using  REST  and  JSON  to  sync  gears between  systems.  It  automates  the provisioning  of  user  accounts  from  HR platforms  into  various  downstream applications.  Understanding  these distinctions  ensures  that  you  apply  the right  protocol  to  the  right  identity challenge.  The  unified  identity ecosystem  is  defined  by  three  essential characteristics.  It  is  layered, specialized,  and  interoperable. Modern  security  requires  a  layered architecture,  one  that  seamlessly  blends internal  on  premises  foundations  with modern  cloud  protocols  to  create  a comprehensive  defense.  Furthermore,  we must  treat  identity  as  a  specialized field.  Authentication,  authorization, and  life  cycle  provisioning  are fundamentally  distinct  problems,  each requiring  its  own  unique  set  of technical  tools.  Finally,  a  mature security  posture  must  be  interoperable. By  utilizing  standards  like  Keraros, SAML,  OIDC,  OOTH  2,  and  SIM  in  strict concert,  we  ensure  full  compliance  and security  without  ever  sacrificing  the user  experience.  Together,  these  pillars form  the  foundation  of  a  modern, resilient  identity  strategy.
