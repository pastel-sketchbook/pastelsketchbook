Welcome  everyone.  Today  we  are  excited to  introduce  AX,  the  distributed  agent runtime,  Google's  open-source foundational  layer  built  to  support autonomous,  resilient,  agentic  loops.  As represented  by  the  technical  blueprint on  this  slide,  AX  is  engineered  to  serve as  a  robust  backbone  for  orchestrating complex,  distributed  agent  networks.  As we  transition  from  simple  model interactions  to  sophisticated, long-running  agentic  workflows,  having  a reliable  runtime  that  ensures  fault tolerance,  seamless  state  management, and  scalability  becomes  absolutely critical.  Over  the  course  of  this presentation,  we  will  explore  how  AX provides  the  essential  infrastructure  to make  these  autonomous  systems  highly resilient  and  ready  for  production environments.  Traditional  AI  agent development  often  starts  with  a monolithic  approach,  where  capabilities are  bundled  into  a  single  code  base. While  simple  to  set  up  initially,  this tightly  coupled  architecture  quickly becomes  a  tangled  web  of  dependencies  as capabilities  grow,  making  the  system incredibly  difficult  to  scale,  isolate, or  audit.  The  AX  distributed  runtime addresses  these  limitations  by  shifting to  a  decoupled,  actor-based Rather  than  running  a  single,  massive application,  this  system  utilizes dynamically  spawned,  isolated  actors managed  by  a  resilient  central  runtime. Each  actor  is  dedicated  to  a  specific capability,  such  as  planning,  rag,  or SQL  execution,  and  the  entire environment  is  optimized  for  Kubernetes via  the  agent  substrate.  This  design ensures  enterprise-grade  scalability, robust  fault  isolation,  and  clear  audit trails  for  every  agent  action.  The architecture  centered  around  the  AX controller  guarantees  that  all communication  streams,  whether originating  from  clients,  agents,  or external  tools,  are  systematically funneled  through  a  single  point  of orchestration.  At  its  core,  the controller  coordinates  these interactions  using  three  critical internal  components.  The  executor  for driving  execution  logic,  the  event  log for  maintaining  a  historical  record,  and the  registry  for  managing  state  and entity  definitions.  Communication  across the  system  is  handled  via  resumable streams,  which  connect  the  controller  to clients,  isolated  agents,  and  external tools,  such  as  MCP  servers  or environment  skills. By  routing  all  user  and  agent  to  calls through  the  single  controller,  the platform  ensures  a  robust,  consistent state  across  the  entire  environment, while  providing  a  unified,  reliable point  for  comprehensive  auditing  and real-time  policy  control.  Maintaining  a reliable  state  during  network interruptions  is  achieved  by  using sequence  numbers  as  precise  markers within  a  durable  event  log. Consider  a  scenario  where  a  client  is receiving  a  stream  of  events, represented  here  by  sequence  numbers  10, 11,  and  12. If  a  disconnection  occurs  immediately after  sequence  11,  the  client  does  not need  to  restart  the  entire  session  or risk  losing  its  place. Upon  reconnecting,  the  client  simply passes  its  last  successfully  received sequence  number,  sequence  11,  back  to the  server. Recognizing  this  exact  marker,  the server  replays  only  the  missed  events that  occurred  after  that  point. This  targeted  recovery  mechanism  ensures that  the  client  and  server  remain perfectly  synchronized  without  the overhead  of  rewinding  or  restarting  the entire  conversation  from  scratch. Managing  workflow  continuity  and experimentation  requires  a  clear understanding  of  the  difference  between acts  resume  and  acts  fork. When  handling  system  interruptions,  acts resume  provides  recovery  by  maintaining the  exact  same  conversation  ID  and replaying  past  events  to  catch  the client  up  to  the  latest  state.
