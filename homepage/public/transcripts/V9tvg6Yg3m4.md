The  fundamental requirement  is  that  if  one  server crashes,  the  system  as  a  whole  must remain  online.  To  achieve  this  level  of resilience,  all  servers  must  flawlessly agree  on  the  exact  same  shared  state. This  consensus  must  be  maintained  even when  networks  fail  or  communication  is disrupted.  As  shown  in  the  diagram,  this shared  state  represents  a  significant point  of  vulnerability  as  any inconsistency  between  nodes  can compromise  the  integrity  and  reliability of  the  entire  system.  Raft  is  a distributed  consensus  algorithm  designed with  a  primary  focus  on understandability. It  achieves  perfect  synchronization across  a  cluster  by  employing  a  model  of strict  centralized  leadership.  In  this system,  a  single  leader  is  elected  to serve  as  the  central  authority.  This leader  is  responsible  for  managing  all state  changes  and  dictating  them  to  the rest  of  the  nodes  in  the  cluster  as illustrated  by  the  diagram.  By  funneling all  updates  through  this  single  point  of control,  Raft  ensures  that  the  entire distributed  system  maintains  a consistent  and  synchronized  state.  Every server  in  a  raft  cluster  operates strictly  within  one  of  three  operational states,  dynamically  shifting  between them  based  on  network  health  and  time. We  begin  with  the  follower  state.  In this  role,  a  node  is  passive  and  only responds  to  incoming  requests.  If  a follower  does  not  receive  communication from  a  leader  within  a  set  time  frame,  a timeout  occurs,  and  the  node  transitions to  the  candidate  state.  As  a  candidate, the  node  actively  campaigns  for leadership  by  seeking  votes  from  its peers.  If  the  node  wins  the  election,  it transitions  to  the  leader  state  where  it manages  the  cluster.  Should  the  leader encounter  a  node  with  a  more  recent  term or  otherwise  need  to  relinquish  control, it  steps  down  and  returns  to  the follower  state,  ensuring  the  continuous and  stable  operation  of  the  cluster.  To prevent  candidacy  collisions  in  a distributed  system,  we  utilize randomized  election  timeouts.  As  shown here,  all  nodes  initially  start  as followers.  To  avoid  the  issue  of simultaneous  elections,  each  node  is assigned  a  randomized  timer.  In  this case,  ranging  from  150  to  300 milliseconds. Since  nodes  B  and  C  have  longer  timers, 200  and  250  milliseconds  respectively, they  are  still  in  the  follower  state when  they  receive  node  A's  request,  they reply  with  a  yes  vote  and  in  doing  so reset  their  own  timers. Continuous  heartbeats  are fundamental  to  maintaining  a  leader's authority  within  a  distributed  cluster. Upon  securing  a  majority  vote,  the designated  leader  immediately  begins transmitting  regular  heartbeat  messages to  all  followers. If  the  leader  crashes  and these  heartbeats  stop  reaching  the followers,  their  election  timers  will eventually  time  out,  triggering  the commencement  of  a  new  election  to restore  cluster  leadership.  Log replication  acts  as  a  synchronized  data pipeline  to  ensure  data  consistency across  a  distributed  system.  This process  follows  a  specific  five-step sequence.  It  begins  in  step  one  when  a client  sends  a  request  such  as  set  x=  5 to  the  cluster's  leader.  In  step  two, the  leader  appends  this  command  to  its own  local  log.  During  step  three,  the leader  replicates  this  log  entry  by sending  it  to  the  follower  nodes.  In step  four,  the  followers  receive  the entry  and  send  back  an  acknowledgement once  it  is  safely  in  their  logs. Finally,  in  step  five,  once  the  leader receives  acknowledgements  from  a  strict majority  of  the  cluster,  it  marks  the entry  as  committed.  Only  then  does  the leader  respond  with  a  success  message  to the  client  and  notify  the  followers  to commit  the  change  to  their  local  states. This  strict  majority  rule  ensures  that changes  are  never  finalized  until  they are  safely  replicated,  maintaining  the integrity  of  the  data  pipeline.
