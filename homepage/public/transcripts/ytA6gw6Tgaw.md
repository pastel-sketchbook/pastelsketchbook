Welcome  to  this  technical  overview  of the  slide  voice  studio  desktop  shell architecture.  As  we  can  see  on  this slide,  our  approach  involves  wrapping  a vite  and  react  single  page  application within  a  zero  IPC  Tory  shell.  This design  allows  us  to  leverage  the  power of  web  technologies  while  maintaining  a lightweight  desktop  presence.  Crucially, this  architecture  supports  a  strictly local  first  workflow,  ensuring  that  data processing  remains  efficient  and private.  To  enhance  this  experience,  the entire  workflow  is  powered  by  the  Google Gemini  API,  providing  advanced intelligence  directly  within  our  local first  environment.  This  slide illustrates  the  strategy  for  bridging web  capabilities  with  a  native  desktop presence.  Starting  with  the  product itself,  we've  developed  a  local  first client  application  that  automates  the creation  of  narrated  videos  from  slide decks.  This  is  achieved  by  integrating the  Gemini  API  for  narration  generation and  utilizing  standard  browser  web  APIs for  video  processing.  The  central constraint  was  the  need  for  a  secure  and installable  native  desktop  environment. Importantly,  this  had  to  be  accomplished without  the  overhead  of  rewriting  an already  robust  and  fully  functional  web codebase.  The  resulting  solution utilizes  a  thin,  highly  constrained Tori2  wrapper  to  maintain  a  rigorous security  posture.  The  wrapper  is configured  with  a  strict  content security  policy  and  operates  with  zero IPC  commands.  This  architecture  allows us  to  deliver  a  native  desktop experience  while  leveraging  the  existing web-based  logic  and  functionality.  This workflow  facilitates  the  transformation of  presentation  slides  into  narrated videos  through  a  streamlined  five-step process.  It  begins  with  the  import  phase where  presentation  files  are  brought  in as  images  or  as  a  PDF  rendered  via PDF.js. In  the  second  stage,  narration  is prepared  by  either  extracting  existing speaker  notes  locally  or  drafting  new scripts  using  the  Gemini  API.  The  third step  involves  voice  generation  utilizing Gemini  texttospech  technology  with  a variety  of  voice  options  such  as  Zephyr, Puck,  and  Fenrir  to  create  the  audio track.  Next,  the  preview  stage  allows for  a  full  review  of  the  synchronized audio  playback  alongside  the  user interface  transitions.  Finally,  the project  is  exported  by  rendering  it  into a  local  video  file  using  the  browser's media  recorder  API.  A  fundamental  aspect of  this  architecture  is  that  all  media, scripts,  and  audio  remain  stored entirely  on  the  local  device,  ensuring complete  data  privacy.  The  core  web stack  presented  here  serves  as  the absolute  source  of  truth  for  our development  architecture.  At  the foundation,  we  utilize  bun  1.3  to consolidate  our  runtime  package  manager and  testrunner  with  biome  handling formatting  to  ensure  a  unified development  experience.  Our  UI  framework layer  leverages  vite  8  and  react  19 paired  with  TypeScript  and  Tailwind  CSS4 for  a  performant  and  type-  safe  front end.  For  state  and  persistence,  we  rely on  local  index  DB,  keeping  data operations  local  to  the  client.  Finally, we  maintain  a  highly  controlled environment  by  limiting  external integration  to  the  Google  Gen  KI library,  which  stands  as  our  sole outbound  network  dependency.  Escaping the  constraints  of  the  browser  tab requires  a  fundamental  shift  toward native  identity  and  strict  system isolation.  Currently,  the  launch experience  is  often  bogged  down  by  local dev  servers  and  generic  browser navigation.  To  address  this,  we  define  a clear  window  contract,  setting  a  default resolution  of  1280x  820  to  match  our desktop  first  React  layouts  while ensuring  responsiveness  down  to  a minimum  of  960x  640.  Beyond  the  layout, achieving  a  true  native  feel  requires  a stable  OS  identity  characterized  by dedicated  task  switching,  persistent  doc icons,  and  integrated  system notifications.  This  transformation  is secured  by  an  unbyassable  OS  level sandbox.  By  implementing  a  content security  policy  that  cannot  be overwritten  by  user  browser  extensions or  dev  tools,  we  ensure  the  high  level of  isolation  and  security  essential  for a  standalone  application.  When evaluating  the  desktop  distribution landscape,  we  examined  five  core technologies  against  four  critical performance  and  development  constraints. While  web  spas  and  progressive  web  apps offer  high  code  reuse,  they  fall  short in  providing  a  stable  OS  identity  or  an unbyassable  content  security  policy. In this  model,  we  move  toward  a  specific architectural  paradigm.  The  shell  owns no  application  state,  no  business  logic, and  no  UI.  By  stripping  away  these responsibilities,  the  shell's  role  is reduced  to  its  core  necessities,  which involve  managing  the  native  OS  window and  enforcing  a  strict  security  policy. This  ensures  that  the  existing  web bundle  remains  the  canonical  artifact  of the  project.  Tori  does  not  transform  the code  or  introduce  proprietary  logic. This  slide  illustrates a  unified  build  pipeline  driven  entirely by  bun  achieving  a  streamlined  workflow for  desktop  application  development.  The core  principle  is  total  exclusivity.  We eliminate  node,  npm,  yarn,  and  pnpm  from the  environment  relying  solely  on  bun for  all  tasks.  The  pipeline  is structured  around  a  single  entry  point where  commands  like  bun  run  towerrydev or  bunr  run  towerry  build  drive  the entire  process.  For  local  development, the  before  dev  command  triggers  bunr rundev,  typically  launching  a  vite server  on  localhost.  For  production,  the before  build  command  initiates  bun  run build.  Both  paths  converge  at  the desktop  binary  generation  phase.  Through efficient  artifact  routing,  Towerry  is configured  to  point  directly  to  the front-end  distribution  directory.  This architecture  ensures  a  consistent  high performance  environment  from  initial development  through  to  the  final production  build.  Our  security architecture  is  built  upon  the  principle of  deliberate  constraint  achieved through  a  nested  security  sandbox.  At the  very  center  lies  the  inner  ring which  encompasses  the  core  vite  and react  webview  user  interface.  Protecting this  core  is  boundary  1  which  enforces  a zero  IPC  environment.  By  ensuring  no towery  commands  are  exposed  and  limiting permissions  strictly  to  the  core default,  we  minimize  the  attack  surface at  the  communication  layer.  Beyond  this, Boundary  2  provides  robust  OS restrictions  where  we  have  intentionally disabled  permissions  for  the  file system,  shell,  system  dialogues,  and HTTP  plugins.  The  final  layer  of  defense is  the  outer  barrier,  which  governs network  access.  A  strict  content security  policy  is  in  place  to  ensure that  outbound  traffic  is  restricted solely  to  Google  Gemini,  creating  a highly  controlled  and  secure  execution environment.  To  ensure  robust  security and  strictly  control  outbound  data  flow, we  implement  several  critical  content security  policy  directives.  For  connect source,  we  limit  connections  exclusively to  our  own  origin  and  specific  Google API  endpoints  required  for  Gemini.  Our worker  source  policy  allows  self  and blob  sources,  ensuring  that  local  PDF.js workers  remain  fully  functional  within the  secure  environment.  Similarly,  media source  and  img  source  are  configured  to permit  self  data  and  blob  schemes  which are  essential  for  the  playback  of locally  generated  texttospech  audio  and the  rendering  of  slide  image  assets.  We maintain  a  very  strict  script  source directive  allowing  only  scripts  from  our own  origin  while  explicitly  prohibiting inline  execution  or  the  use  of  eval. Finally,  to  prevent  unauthorized embedding  or  plug-in  based  attacks,  we have  set  object  source  base  URI  and frame  ancestors  to  none.  Maintaining  a near  zero  footprint  in  the  Rust  surface is  a  key  architectural  objective.  To achieve  this,  we  utilize  a  code  delegate pattern  where  the  main  entry  point  is reduced  to  a  single  line  delegate.  This specific  structure  enables  the  crate  to compile  as  various  library  targets including  static  libraries,  C  compatible dynamic  libraries  and  standard  RS libraries.  By  adopting  this  approach,  we eliminate  the  need  for  custom  commands, state  management,  external  plugins,  and event  subscriptions  within  this  layer. This  streamlined  design  minimizes overhead  and  ensures  that  the  Rust integration  remains  as  lightweight  and efficient  as  possible.  The  zero  IPC wrapper  approach  provides  four  key architectural  benefits.  First,  it establishes  a  single  source  of  truth. Because  every  feature  lives  within  the web  bundle,  the  desktop  shell  cannot drift  out  of  par,  ensuring  consistent behavior  across  updates.  Second,  this model  offers  a  tight  blast  radius.  Even if  an  XSS  vulnerability  occurs  inside the  web  view,  it  remains  isolated  and cannot  access  host  file  systems  or arbitrary  networks.  Third,  maintenance is  significantly  simplified.  Upgrading your  Tori  version  is  a  straightforward process  involving  only  a  version  bump  in the  cargo.l  file  and  a  quick  CLI  update using.  Finally,  this  approach  provides mobile  ready  scaffolding.  By  compiling the  core  application  as  a  library,  you can  seamlessly  transition  to  iOS  or Android  platforms  in  the  future  without requiring  any  major  architectural restructuring.  Acknowledging  the inherent  trade-offs  and  current limitations  is  crucial  to  setting realistic  expectations  for  our development  roadmap.  At  present,  we  do not  have  a  native  escape  hatch.
