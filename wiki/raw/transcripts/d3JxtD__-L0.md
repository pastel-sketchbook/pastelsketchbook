Welcome  everyone.  Today  we're  embarking on  an  exciting  journey  into  the architecture  of  modern  game  and simulation  engines.  Our  focus  will  be  on architecting  a  modern  Robocode  engine, specifically  detailing  how  we  can leverage  the  robust  capabilities  of  Rust and  the  efficient  design  patterns  of  a bevy  ECS  blueprint.  This  session  aims  to lay  out  a  comprehensive  guide  for building  high  performance,  maintainable, and  scalable  systems  for  competitive programming  environments  like  Robocode using  a  truly  modern  tech  stack.  The rebirth  of  an  educational  classic  is underway,  transforming  IBM's  original Java  Robocode.  Initially  developed  by Matthew  Nelson,  this  seinal  project  was known  for  its  objectoriented  plug-in  AI offering  a  powerful  platform  for learning  programming  concepts.  Moving forward,  this  classic  is  being reimagined  with  a  cuttingedge  foundation leveraging  Rust  and  Bevy  ECS.  This modern  approach  delivers  datadriven determinism  and  a  robust  memory  safe architecture  greatly  enhancing performance  and  stability  for  a  new generation  of  learners.  This  slide illustrates  our  workspace  architecture emphasizing  a  clear  separation  of concerns  across  different  components.  At the  foundational  level,  we  have  two distinct  ways  to  implement  bots.  The bots/directory houses  native  dynamic  libraries, specifically  cdy  libs,  offering  full system  access  and  performance. Complementing  this,  bots_wam/ contains  sandboxed  web  assembly  modules providing  a  secure  and  portable execution  environment.  Both  native  and  W was  bots  interact  through  the  bot  API layer  which  acts  as  the  crucial interface.  This  API  defines  the  bot trait  establishing  the  common  contract that  all  bots  must  adhere  to.  It provides  a  context  for  bot  operations, handles  events  that  trigger  bot  logic and  exposes  commands  that  bots  can execute  or  respond  to.  This standardization  ensures  consistent communication  regardless  of  the  bot's underlying  implementation. Finally,  the  bot  API  layer  itself integrates  with  the  core  engine.  The engine  is  built  upon  the  bevy  ECS  or entity  component  system  paradigm, managing  the  application  state  and  logic through  systems.  It  also  incorporates robust  plug-in  loaders  designed  to dynamically  load  both  native  and  web assembly  components,  tying  the  entire architecture  together  and  enabling extensibility.  Understanding  a  robot's interaction  with  its  environment  begins with  its  API  which  structures  how  it perceives  and  acts  upon  the  world.  This API  is  segmented  into  three  core components.  First,  we  have  the  sensors providing  readonly  state  information. This  includes  the  robot's  own  self  state such  as  its  energy  levels,  heat signature,  and  current  heading.  It  also provides  arena  state,  giving  context about  the  battleground,  including  the current  game  tick  and  environmental dimensions.  Next,  the  inbox  serves  as the  robot's  event  listener.  Here,  it receives  various  bot  events,  signaling important  occurrences.  Examples  include detecting  a  scanned  bot,  indicating another  robot  has  been  observed,  or receiving  a  hit  by  bullet  event, informing  the  robot  it  has  taken  damage. Finally,  the  actuators  represent  the commands  a  robot  can  issue  to  influence its  environment.  These  bot  commands enable  actions  like  move  to  change  its position,  turn  to  adjust  its orientation,  and  fire  to  engage  targets. It's  crucial  to  note  that  this  entire context  encompassing  sensor  data, incoming  events,  and  available  commands is  securely  provided  by  the  engine  as  a snapshot  with  every  tick.  This  design ensures  that  no  raw  entity  component system  access  is  permitted,  maintaining a  controlled  and  secure  operational environment  for  each  robot.  The  event routing  problem  addresses  how  we efficiently  manage  and  distribute  a multitude  of  incoming  game  events.  Bevy events,  as  illustrated  at  the  top,  are global.  Diverse  occurrences  such  as  an E-scanned  bot  detection,  an  e-hitby bullet  impact,  or  an  e-hit  wall collision  all  originate  within  this single  global  stream.  This  global  nature initially  presents  an  O  of  N  complexity for  event  processing.  To  mitigate  this, all  these  global  events  are  fed  into  our centralized  event  router  system,  which is  depicted  as  a  funnel  with  gears.  This system's  core  purpose  is  to deterministically  map  these  O  ofN  global events  into  isolated  O  of  one  inboxes. As  demonstrated  at  the  bottom,  the router  effectively  dispatches  relevant events  to  individual  perbot  inboxes, ensuring  each  bot  receives  only  the information  it  needs,  thereby  optimizing performance  and  maintaining predictability.  Subsystem  one,  dedicated to  kinematics  and  movement,  is  crucial for  controlling  the  bot's  physical presence  in  its  environment.  This  module receives  turn  and  move  commands  which are  then  processed  by  the  bot  kinematics component.  Within  bot  kinematics,  the system  models  the  bot's  physical properties,  including  its  maximum  speed, acceleration,  and  turn  rate  to accurately  simulate  its  movement.  As  a result,  the  subsystem  generates  a refreshed  transform,  providing  real-time updates  on  the  bot's  position  and heading.  Furthermore,  it  triggers  an  eh hit  wall  event  if  a  collision  with  a boundary  occurs,  signaling  other  systems to  respond  to  this  interaction. Subsystem  2  focuses  on  the  deterministic radar  geometry  that  governs  target detection.  Here  we  observe  the  scanner emitting  a  defined  field  of  view  or  FOV which  has  a  specific  max  distance.  The scanner's  heading  establishes  the central  axis  of  this  conical  scanning area.  When  the  target  falls  within  this FOV  and  its  hit  radius  intersects  with the  scanned  space,  it  is  successfully detected.  This  interaction  generates  an escanned  bot  output,  providing  critical data  points  such  as  the  target's distance,  bearing  relative  to  the scanner,  and  its  energy.  To  guarantee flawless  replication  and  consistent outcomes  across  all  matches,  a  strict squared  distance  and  angle  check  runs synchronously,  ensuring  absolute determinism  in  radar  detection. Subsystem  3  defines  our  decoupled projectile  simulation,  outlining  the four  distinct  stages  a  projectile undergoes  from  its  creation  to  impact. The  process  begins  with  spawn,  where  the bullet  entity  is  first  created.  In  this stage,  its  power  and  speed  attributes are  carefully  clamped  to  predefined limits,  establishing  its  initial conditions.  Next,  during  flight,  the bullet  travels  through  the  environment. A  crucial  aspect  of  this  decoupled system  is  that  the  bullet's  velocity  is integrated  into  its  transform independently  of  the  shooter.  This  means once  fired,  the  projectile's  trajectory and  movement  are  simulated  on  their  own, separate  from  the  firing  entity.  The third  stage  is  collision.  This  occurs when  the  projectile's  path  intersects with  a  target's  defined  hit  radius, indicating  a  physical  contact.  Finally, at  impact,  two  distinct  events  are generated.  The  e  hit  by  bullet  event  is dispatched  specifically  to  the  victim, informing  them  of  the  hit,  while  the  e bullet  hit  event  is  sent  to  the  shooter, confirming  their  successful  shot. Central  to  our  architecture  is  the deterministic  game  loop,  a  synthesis designed  for  predictable  and reproducible  gameplay.  It  begins  with step  one  where  we  apply  motion  commands effectively  updating  each  bot's  intended movement  for  the  current  frame. Following  this,  the  movement  system executes,  handling  physics  and registering  events  such  as  EIT  wall  if  a bot  collides  with  terrain.  Next,  step three,  the  bullet  simulation  progresses all  active  bullets,  identifying  EIB  by bullet  and  E  bullet  hit  events. Subsequently,  the  scanning  system  allows bots  to  perceive  their  environment, generating  escanned  bot  events  for  any detected  opponents.  Death  detection  then occurs  in  step  five,  identifying  and registering  Ebot  death  events  for  any bots  whose  health  has  dropped  to  zero. All  these  generated  events  from  global chaos  are  then  routed  to  their respective  perbot  inboxes  during  step six.  This  leads  us  to  the  critical  bot tick  in  step  seven,  where  each  bot's plugins  execute  their  logic  based  on  the events  received  in  their  inbox, determining  their  actions  for  the  next frame.  Based  on  these  decisions,  apply fire  commands  in  step  eight,  spawn  any new  bullets.  Finally,  step  9  clears  all inboxes,  resetting  them  to  prepare  for the  events  of  the  subsequent  frame.  This structured  sequence  ensures  every  game frame  is  processed  identically, guaranteeing  determinism.  Examining  our plug-in  architecture  reveals  a fundamental  comparison  between  native and  WASOM  approaches  for  sandboxing. Native  plugins  typically  built  as  C dilib  offer  open  system  access  implying a  lower  level  of  isolation  but  greater flexibility.  In  contrast,  WAM  plugins aswum  binaries  provide  a  strictly isolated  runtime  environment  enhancing security  and  predictability.  When considering  the  type  system,  native plugins  benefit  from  rich  Rust  traits and  enos  allowing  for  complex  and expressive  data  structures.  WAM  however relies  on  a  flat  application  binary interface  or  AI  primarily  using  strrus and  integers  which  simplifies interoperability  but  can  require  more manual  data  marshalling.  Regarding  build output,  native  plugins  generate  platform specific  files  such  as  for  Linux  ordlls. WAM  plugins  on  the  other  hand  produce  a universalwam  binary  which  can  run  across various  platforms  without  recompilation. Finally  in  terms  of  execution  native plugins  offer  direct  memory  execution making  them  the  fastest  option.  Wom plugins  are  executed  within  a  WAM  time or  WASMR  runtime  achieving  near  native performance  which  is  still  highly efficient.  Crucially,  our  engine  is designed  to  support  both  plug-in  types, effectively  decoupling  the  core  game loop  from  the  specific  execution environment  and  offering  developers flexibility  in  how  they  extend functionality.  Crucially,  when  data crosses  the  WASM  memory  boundary,  it undergoes  a  significant  transformation from  rich  Rust  types  to  a  more  primitive representation.  On  the  engine  side,  we might  begin  with  a  structured  event  like botevent.scannedbot containing  fields  such  as  distance  and bearing.  As  this  data  prepares  to traverse  the  boundary,  it  is  tagged  with #repper  C  and  converted  into  raw pointers,  effectively  flattening  its structure.  Once  across  this  interface, the  sandboxed  WASOM  environment  receives this  information  as  a  simplified  WAM event,  typically  represented  with  basic types  like  F-32  for  its  constituents, often  accompanied  by  a  kind  identifier to  denote  the  event  type.  The  key takeaway  here  is  fundamental.  No  rich rust  traits  or  complex  abstractions directly  cross  this  boundary.  Instead, the  state  is  meticulously  serialized into  flat  memory  pointers  which  are  then parsed  and  reconstructed  by  the sandboxed  guest.  This  particular architecture  provides  an  exceptional pedagogical  framework  for  mastering  Rust specifically  due  to  three  core  areas. First,  our  approach  emphasizes  Rust's fundamental  concepts  of  ownership  and borrowing.  The  carefully  designed  bot context  API  restricts  direct  raw  access to  the  underlying  entity  component system.  This  restriction  inherently compels  students  to  adopt  safe  state handling  practices,  ensuring  they  grasp Rust's  memory  safety  guarantees  from  the outset  without  needing  to  navigate  the complexities  of  raw  ECS  operations directly.  Next,  the  architecture cultivates  a  deep  understanding  of entity  component  system  or  ECS  thinking. Students  learn  to  translate  conventional object-oriented  programming  logic  into Bevy's  highly  efficient,  datadriven,  and strictly  ordered  components  and  systems. This  paradigm  shift  is  crucial  for writing  performant  and  maintainable  REST code,  especially  in  game  development  and other  complex  simulations.  Finally,  the system  inherently  involves  dynamic dispatch  and  foreign  function  interface or  FFI  interactions.  The  process  of building  and  dynamically  loading external  libraries  or  web  assembly modules  provides  invaluable  hands-on experience  in  real  world  plug-in engineering.  This  skill  set  is  essential for  creating  extensible  applications  and integrating  Rust  with  other  languages and  ecosystems.
