Welcome  to  our  session  on  mastering hybrid  CDC  architectures.  Today  we  will explore  the  architectural  patterns  and best  practices  required  to  build efficient  realtime  data  streaming pipelines.  Looking  at  the  flow  on  the screen,  our  journey  starts  with  a localized  SQL  database  which  acts  as  our primary  system  of  record.  To  enable  data mobility,  we  employ  change  data  capture or  CDC  processing  through  Debeesium. This  layer  captures  every  insert, update,  and  delete  event  from  the database  logs  and  prepares  them  for downstream  consumption.  These  events  are then  transmitted  to  our  message  Q, Rabbit  MQ,  which  provides  the  necessary decoupling  and  reliability  for  our distributed  systems.  Throughout  this presentation,  we  will  provide  a  deep dive  into  the  best  practices  for managing  SQL  Server,  Debeesium,  and Rabbit  MQ.  Specifically  focusing  on  how to  maintain  data  persistence  and scalability  using  Kubernetes  stateful storage.  The  journey  of  stateful  data begins  in  zone  1,  our  on-remise  source, where  a  SQL  server  acts  as  the  initial database  buffer.  Data  then  transitions into  zone  2,  the  hybrid  network, crossing  a  low  latency  bridge  designed for  secure  and  rapid  transmission between  local  and  cloud  environments. The  journey  concludes  in  zone  3  within  a cloud-based  Kubernetes  cluster.  Here, the  engine  operates  inside  a  pod interacting  with  persistent  storage  to maintain  the  state  while  simultaneously directing  data  flow  to  the  sync  for final  consumption.  To  understand  how Kubernetes  decouples  compute  from  data, we  must  examine  the  relationship  between the  pod,  the  persistent  volume  claim, and  the  persistent  volume.  When  a  pod requires  storage,  it  issues  a  persistent volume  claim  or  PVC.  You  can  think  of the  PVC  as  a  formal  request  or  a  ticket where  the  pod  declares  exactly  how  much capacity  and  what  type  of  access  it needs.  Kubernetes  then  takes  this  claim and  binds  it  to  a  matching  persistent volume  or  PV.  The  PV  represents  the actual  physical  storage  medium  such  as an  AWS  EBS  volume  or  a  Google  Cloud Desk.  To  automate  this  process,  we  use  a storage  class.  The  storage  class  serves as  an  automated  blueprint  instructing Kubernetes  on  exactly  how  to  dynamically provision  a  new  PV  on  the  fly  whenever  a PVC  is  created.  This  architecture ensures  that  compute  resources  remain independent  from  the  underlying  physical storage,  allowing  for  seamless scalability  and  management. Scaling  storage  requirements  effectively depends  on  the  environment  and  the specific  needs  of  your  application.  When starting  with  local  development,  a simple  approach  using  the  hostgath method  is  common.  This  involves  mapping a  node's  physical  directory  directly  to a  pod,  which  works  well  for  simple  use cases  like  a  local  SQLite  database. However,  it  is  important  to  remember that  this  method  is  ephemeral  and  lacks reliability  in  multi-node  clusters.  As we  move  into  intermediate  cloud-based environments,  we  often  transition  to dynamic  provisioning  within  deployments. This  is  a  standard  approach  for  services such  as  user  upload  servers.  A significant  caveat  here  is  that  drives using  read  write  once  access  modes  can cause  scaling  conflicts.  If  your replicas  are  scheduled  on  different nodes,  they  will  be  unable  to  attach  to the  same  volume  leading  to  operational failures.  For  complex  production requirements,  particularly  for distributed  databases,  we  utilize stateful  sets  combined  with  volume  claim templates.  This  configuration  acts  as  a factory,  ensuring  each  replica  is automatically  provisioned  with  its  own dedicated  persistent  drive.  This provides  the  necessary  statefulness  and individual  storage  management  required for  robust  enterprise  level applications.  Capturing  data  from  SQL server  using  change  data  capture  or  CDC involves  specific  architectural considerations  that  differ  from  other platforms.  To  ensure  a  reliable  data pipeline,  we  must  manage  three  primary operational  risks.  First  is  agent dependency.  Unlike  Postgrasell,  SQL Server  CDC  relies  on  internal  log  scan jobs  executed  by  the  SQL  Server  agent. If  the  agent  stops,  Debeesium  will  show zero  changes  even  while  production  data continues  to  update,  creating  a  silent failure  in  your  data  synchronization. Second,  we  must  prioritize  log management.  The  transaction  log  orlddf file  should  always  reside  on  high performance  storage.  Because  CDC prevents  the  log  from  being  truncated until  it  has  been  processed,  a  slow capture  job  can  cause  the  log  to  fill the  entire  disc.  If  this  occurs,  the entire  database  will  hang,  leading  to significant  downtime.  Finally,  there  is the  identity  blind  spot.  Truncate operations  bypass  the  transaction  log entries  that  CDC  monitors,  meaning Debeesium  will  never  see  these  events. To  ensure  that  your  downstream  systems stay  in  sync,  you  must  always  use  delete operations  rather  than  truncate  for  any tables  participating  in  an  event  stream. Bridging  the  network  gap  between  on premises  infrastructure  and  the  cloud requires  a  multi-layered  approach  to ensure  reliability  and  performance. First,  establishing  a  low  latency interconnect  is  non-negotiable.  Using  a dedicated  VPN  or  express  route  is mandatory  as  standard  public  endpoints introduce  excessive  latency.  This latency  directly  impacts  the  SQL  server leading  to  dangerous  log  lag  that  can compromise  data  integrity  and synchronization. To  manage  connectivity  within  a Kubernetes  environment,  we  implement headless  service  routing.  By  creating  a K8  service  without  selectors  and defining  a  manual  endpoint  that  points to  the  on-  premises  IP,  we  provide Debeesium  with  a  stable  DNS  name  such  as SQL  server.SVC. This  abstraction  allows  the  system  to survive  physical  IP  migrations  without requiring  manual  configuration  changes or  downtime.  Finally,  we  address  the challenge  of  massive  data  transfers through  incremental  snapshots.  Initial 500  GBTE  table  snapshots  are  prone  to failure  over  a  VPN  due  to  network instability.  By  utilizing  signaling tables,  Dezium  can  perform  incremental snapshots,  allowing  it  to  resume  data chunks  seamlessly  following  a  network drop.  This  ensures  that  even  large  data sets  are  migrated  reliably  without starting  from  scratch  after  every interruption.  To  effectively  tune  a standalone  debzium  engine  within  a Kubernetes  environment,  we  must  focus  on three  critical  configuration  areas.  The controller,  the  update  strategy,  and resource  management.  First,  let's examine  the  controller.  We  deploy  the DBZM  server  as  a  standard  Kubernetes deployment,  but  it  must  be  configured  as a  singleton  with  exactly  one  replica. Because  DESM  maintains  a  specific  offset to  track  database  changes,  running multiple  instances  concurrently  could lead  to  data  inconsistency  or  duplicate event  processing.  Next,  we  look  at  the deployment  strategy.  It  is  essential  to set  the  strategy  type  to  recreate  rather than  the  default  rolling  update.  In  a standard  rolling  update,  Kubernetes attempts  to  start  a  new  pod  before  the old  one  is  terminated.  Since  Debeesium requires  exclusive  access  to  a persistent  volume  to  store  its  state, this  overlap  causes  a  mounting  conflict where  both  pods  attempt  to  lock  the  same volume.  Using  the  recreate  strategy ensures  the  existing  pod  fully  releases the  volume  before  the  new  instance starts.  Finally,  we  must  define  strict resource  limits.  DBZM's  initial  snapshot phase  is  incredibly  memory  intensive  as it  reads  the  existing  state  of  the source  database.  Failing  to  set  these limits  is  a  primary  cause  of  Kubernetes own  kills  as  the  process  will  otherwise expand  until  it  exhausts  the  node's available  memory.  By  defining  explicit CPU  and  memory  boundaries  such  as  the  1 GB  of  CPU  and  2  GB  of  memory  shown  here, we  ensure  the  engine  operates  within  a stable  and  predictable  environment.  The core  logic  of  change  data  capture specifically  within  a  DESium  environment resides  in  two  essential  files.  The offset  storage  and  the  schema  history. Together  they  act  as  the  brain  of  the operation.  Offset  storage,  represented by  the  offsets.dat  file,  is  responsible for  tracking  the  log  sequence  number  or LSN.  This  tells  the  connector  exactly where  it  left  off  in  the  database's transaction  log.  To  ensure  continuity, it  is  vital  to  store  this  file  on  a persistent  volume,  like  a  high performance  SSD.  If  the  pod  restarts  and this  data  is  not  persisted,  DESium  loses its  markers  and  is  forced  to  rescan  the entire  database  from  its  inception, which  can  be  a  massive  performance  hit. The  second  component  is  the  schema history  stored  in  schema  history.dat. This  file  records  all  data  definition language  changes  over  time.  Because database  structures  evolve,  Debeesium needs  this  history  to  correctly interpret  the  data  it  reads  from  old transaction  logs.  There  is  a  critical interdependency  here  that  demands attention.  If  you  maintain  your  offsets but  lose  your  schema  history,  Debeesium will  try  to  process  log  entries  without understanding  the  historical  column structure  leading  to  a  system  crash.  For a  resilient  CDC  architecture,  these  two files  must  always  be  managed,  backed  up, and  restored  as  a  single  synchronized unit.  Navigating  Kubernetes  storage requires  an  understanding  of  several architectural  traps  that  can  impact  data persistence  and  application availability. The  first  trap  is  the  reclaim  policy. Most  dynamically  provisioned  persistent volumes  default  to  a  delete  reclaim policy.  This  poses  a  significant  risk because  deleting  a  namespace  will permanently  destroy  the  associated  cloud drive.  To  protect  your  data,  it  is  a best  practice  to  patch  critical persistent  volumes  to  the  retain  policy. The  second  trap  is  the  availability  zone deadlock.  This  occurs  when  a  cloud provider  creates  a  disk  in  one  zone,  but the  Kubernetes  scheduler  places  the corresponding  pod  in  a  different  zone. Since  disks  cannot  cross  zone boundaries,  the  pod  remains  stuck  in  a pending  state.  The  fix  is  to  configure your  storage  class  with  the  wait  for first  consumer  volume  binding  mode.  This ensures  that  disc  creation  is  delayed until  theuler  has  determined  the  pod's node  placement  guaranteeing  zone alignment.  Finally,  we  must  distinguish between  readwrite  once  and  read  many access  modes.  Standard  cloud  block storage  is  restricted  to  RWO,  meaning only  one  node  can  mount  the  volume  at  a time.  File  storage  solutions  such  as  NFS or  Amazon  EFS  provide  RWX  capabilities for  multiode  access.  Note  that specialized  workloads  such  as  those requiring  change  data  capture  or  CDC specifically  require  the  performance characteristics  of  block  storage. Orchestrating  the  Rabbit  MQ  sync effectively  requires  moving  beyond standard  Kubernetes  primitives.  The golden  path  for  deployment  is  to  use  the official  Rabbit  MQ  operator  rather  than raw  stateful  sets.  This  approach automates  the  complex  logic  necessary for  clustered  messaging,  handling configurations  that  would  otherwise  be prone  to  manual  error.  One  of  the  most critical  advantages  of  using  the operator  is  parallel  management. Standard  Kubernetes  stateful  sets default  to  an  ordered  ready  policy  which can  lead  to  raft  cluster  deadlocks  in Rabbit  MQ  environments.  The  operator solves  this  by  safely  setting  the  pod management  policy  to  parallel.  This allows  all  nodes  to  negotiate  cluster membership  simultaneously,  ensuring  a smoother  and  more  reliable  startup process.  Furthermore,  we  utilize  the topology  operator  to  bridge  the  gap between  infrastructure  and  application logic.  This  allows  us  to  define  rabbit MQs  and  exchanges  directly  as  native Kubernetes  YAML  objects.  By  managing  our messaging  topology  through  the  same declarative  patterns  as  our infrastructure,  we  achieve  better consistency  and  easier  life  cycle management  across  our  entire  stack. Engineering  Rabbit  MQ  for  zero  data  loss requires  a  fundamental  shift  from classic  QES  to  quorum  QES.  While  classic QES  are  vulnerable  to  data  loss  during network  partitions,  quorum  QES  are  the mandatory  choice  for  highstakes  change data  capture  workloads.  By  employing three  replicas,  each  with  its  own dedicated  persistent  volume,  we  ensure data  durability.  Even  if  an  entire availability  zone  fails,  the  remaining two  disks  retain  the  complete  data  set. Storage  performance  is  equally  vital since  CDC  is  an  inherently  chatty process  that  generates  significant  write activity.  To  maintain  the  write-  ahead log,  you  must  utilize  high  IOPS  SSDs such  as  Azure  managed  premium  or  AWS GP3.  Lastly,  to  ensure  rapid  recovery from  hardware  failures,  we  must  address the  issue  of  zombie  volumes.  Enabling the  node  problem  detector  allows  for  the forceful  detachment  of  volumes  from failed  nodes,  unblocking  replacement pods  and  ensuring  immediate  system continuity.  In  an  incident  response scenario,  we  must  account  for  the dynamics  of  data  synchronization  during a  recovery  event.  This  process  generally follows  three  stages.  Phase  one  is  the buffer.  When  a  Kubernetes  cluster  goes offline,  the  source  system,  in  this case,  an  on-remise  SQL  server,  continues to  function  normally.  It  continues capturing  changes  into  its  internal  CDC tables,  safely  buffering  data  until  the downstream  services  are  restored.  Phase two  is  the  restoration.  As  the Kubernetes  cluster  comes  back  online, Dezium  initializes  it  mounts  its persistent  volume  and  reads  the offsets.dat  file  to  determine  its  last known  position.  At  this  point,  the system  identifies  that  it  is significantly  behind  the  current  log sequence  number  or  LSN.  Phase  3  is  the spike.  To  catch  up,  Debeesium  begins speedreading  the  database  logs.  This rapid  data  ingestion  causes  a  massive temporary  spike  in  network  usage  across the  VPN.  This  intense  activity  persists until  the  backlog  is  cleared  and  the system  returns  to  its  steady,  real-time state.  Our  disaster  recovery  master  plan is  designed  to  facilitate  a  rapid  and reliable  failover  from  a  primary  region to  a  secondary  active  site.  In  a scenario  where  region  A  is  rendered unavailable,  we  maintain  continuity across  three  critical  architectural layers.  For  the  database  layer,  we utilize  SQL  server  availability  groups to  ensure  continuous  synchronization between  regions.  This  provides  a  robust failover  mechanism  for  our  data  tier.  At the  Kubernetes  layer,  we  employ  Valero to  back  up  our  cluster  manifests  and orchestrate  CSI  volume  snapshots, allowing  for  the  consistent  restoration of  our  containerized  infrastructure  and persistent  volumes.  Finally,  for  the message  layer,  we  leverage  Rabbit  MQ federation  and  shovel  to  seamlessly route  messages  to  a  passive  cluster  in region  B.  This  integrated  strategy ensures  that  our  data  orchestration  and asynchronous  communication  remain resilient  in  the  face  of  a  regional disaster.  This  production  configuration playbook  outlines  the  infrastructure requirements  for  our  critical  system components.  For  Dezium  offsets,  we utilize  high  performance  SSDs  with  the read  write  once  access  mode  to  ensure low  latency  operations.  The  disaster recovery  strategy  involves  CSI  volume snapshots  via  Valero  executed  every  hour to  maintain  data  integrity  and  minimize recovery  point  objectives.  Next,  for Rabbit  MQ  data,  we  also  leverage  high performance  SSDs  and  the  read  write  once access  mode  to  support  high  throughput messaging  requirements.  Resilience  is built  in  through  the  use  of  quorum  cues maintaining  a  minimum  of  three  replicas to  ensure  high  availability  and  data persistence  across  nodes.  Finally, schema  history  is  hosted  on  standard SSDs  with  a  read  write  once  access  mode as  its  performance  requirements  are  less intensive.  To  ensure  consistency  during a  recovery  event,  backups  for  schema history  are  performed  in  tandem  with  our offsets  and  stored  in  object  storage. This  strategic  configuration  ensures that  each  component  is  optimized  for performance  while  remaining  protected  by a  robust  disaster  recovery  framework. The  fundamental  philosophy  guiding modern  architecture  is  that  compute  is ephemeral  while  data  is  permanent.  In  a containerized  ecosystem,  compute resources  are  transient  by  design, intended  to  be  destroyed  and  replaced within  seconds.  Because  of  this  inherent volatility,  building  a  resilient  change data  capture  architecture  requires  a strategic  shift  in  focus.  We  must  look beyond  application  logic  and  prioritize the  physical  storage  primitives  that  sit beneath  it.  As  the  central  visual illustrates,  while  various  compute instances  may  spin  up  or  down,  the  core data  storage  remains  the  stable, constant  hub  of  the  system.  Ultimately, mastering  stateful  storage  is  the critical  requirement  for  unlocking  true zero  data  loss  event  streaming.
