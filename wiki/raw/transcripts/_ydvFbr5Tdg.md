Understanding  the  division  of  labor between  a  custom  resource  definition  or CRD  and  an  operator  is  fundamental  to extending  Kubernetes.  On  one  hand,  the CRD  serves  as  the  static  data  model  and schema.  Its  nature  is  purely declarative,  registering  a  new  API  type such  as  a  Kafka  cluster  within  the Kubernetes  environment. Ultimately,  a  CRD  on  its own  is  simply  a  schema  allowing  for  new YAML  storage.  It  is  the  operator  that provides  the  engine,  bringing  that declarative  blueprint  to  life. Levelbased  design  is  the  foundational architecture  powering  the  Kubernetes reconciliation  loop,  ensuring  high reliability  through  continuous  state evaluation  rather  than  simple eventdriven  reactions.  This  continuous cycle  operates  in  four  key  phases.  First at  the  top,  the  controller  observes  the custom  resource  definition  or  CRD instance  to  capture  the  current environment.
