Welcome  everyone.  Thank  you  for  joining us  for  this  architecture  review  of TN-file  upload.  Today  we  will  explore the  design  and  implementation  of  this production-grade  streaming  first  gRPC file  service  built  entirely  in  Rust. We'll  delve  into  how  this  system  handles high  performance  file  transfers,  its core  architectural  components,  and  the specific  advantages  of  using  Rust  for  a service  of  this  nature.  Let's  get started.  Our  project  mandate  is  to deliver  a  scalable  memory  efficient upload  and  download  service  specifically engineered  to  handle  large  files  without resource  exhaustion.  Our  core  technology stack  is  built  on  Rust  1.95  or  higher, leveraging  the  Tokyo  asynchronous runtime,  tonic  for  gRPC  communications, and  Axom  as  our  REST  shim.  To  ensure performance  and  reliability,  we  have implemented  key  capabilities  such  as client  and  serverside  chunked  streaming, pluggable  storage  traits,  and  real-time Shaw  256  validation  for  data  integrity. From  a  deployment  perspective,  the service  is  Kubernetes  ready, incorporating  tonic  health  probes  and support  for  graceful  HTTP2  goaway shutdowns  to  facilitate  seamless operational  transitions.  Let's  examine the  traditional  approach  to  handling large  data  transfers  using  REST multiart.  In  this  model,  the  server  is often  forced  to  buffer  the  entire request  body  into  memory  before  it  can be  processed  or  stored.  This  memory buffer  creates  a  significant  bottleneck as  memory  consumption  scales  directly with  the  size  of  the  payload,  risking system  exhaustion  when  dealing  with massive  data  sets.  GRPC  streaming  offers a  more  efficient  solution  to  this challenge.  By  leveraging  HTTP2 multipplexing,  the  data  is  broken  down into  small  protobuff  chunks.  These chunks  are  transmitted  and  processed individually  strictly  as  they  arrive eliminating  the  need  for  large-scale buffering  on  the  server  side.  The ultimate  result  is  strictly  bounded memory  usage.  This  architecture  ensures that  the  memory  footprint  remains constant  and  predictable  providing  the same  level  of  performance  and  stability whether  you  are  transferring  a  1  kilob file  or  a  100  GB  payload.  Our architecture  is  organized  into  three distinct  core  layers  complemented  by  two specialized  auxiliary  components.  At  the entry  point,  layer  1  handles  our interceptors.  This  layer  manages crosscutting  infrastructure  concerns including  UUID  injection  for  request tracking,  distributed  tracing,  and initial  authentication  validation. Moving  into  the  core  logic,  layer  2 contains  the  file  upload  service.  This service  is  responsible  for  managing  gRPC streaming  life  cycles,  enforcing  chunk size  limits,  and  ensuring  protocol specific  validation.  Below  this  sits layer  3,  the  storage  layer.  By  utilizing an  arc  wrapped  dynamic  storage  trait,  we have  created  an  abstracted  persistence layer  that  currently  defaults  to  the local  file  system,  but  remains  decoupled from  the  service  logic  for  future extensibility.  On  the  periphery,  we include  two  supporting  services.  To  the left,  the  Axom  REST  shim  provides  a secondary  REST  API  interface specifically  designed  to  support browserbased  single  page  applications. To  the  right,  the  Tonic  health  service offers  isolated  health  probes,  providing the  necessary  signals  for  Kubernetes  to manage  container  health  and  traffic routing  independently  of  the  main service  execution.  This  slide illustrates  the  flow  from  the  wire protocol  to  the  storage  trait,  detailing how  client  requests  are  translated  into storage  operations.  The  process  begins at  the  client  level  where  the  initial step  is  sending  the  upload  metadata.  On the  service  side,  the  wire  protocol layer  validates  this  metadata  against  a protobuff  one-of  schema.  This  design provides  essential  type  safety, guaranteeing  that  metadata  is  always  the first  message  received  in  the  stream. Once  validation  is  successful,  the service  invokes  the  create  method  on  the storage  trait.  Following  this  initial handshake,  the  client  begins  sending data  chunks.  The  service  processes  these bite  chunks  and  executes  a  corresponding append  operation  in  a  loop  on  the storage  trait.  After  all  chunks  are processed,  the  life  cycle  concludes  with a  call  to  the  finalize  method.  Three core  principles  underpin  this architecture.  First,  type  safety  is enforced  through  schema  guarantees. Second,  we  employ  a  fail  fast  design.  If the  initial  metadata  is  rejected,  the stream  terminates  immediately  which prevents  unnecessary  bandwidth  usage. Finally,  we  maintain  an  explicit  life cycle  where  the  wire  protocol  stages  map directly  one  to  one  with  the  storage trait  methods  ensuring  a  predictable  and robust  implementation.  Our  current architecture  utilizes  the  arc  dine storage  trait  as  a  central  abstraction layer.  Presently  the  system  ships  with  a local  storage  backend  leveraging  the async  trait  macro  for  efficient  dynamic dispatch.  This  design  ensures  that  our service  logic  remains  entirely  decoupled from  the  underlying  storage implementation.  As  a  result,  the platform  is  futurep  proof.  We  can integrate  additional  object  stores  such as  AWSS  S3,  Google  Cloud  Storage  or Azure  with  zero  modifications  to  the gRPC  service  layer.  Furthermore,  by splitting  the  data  life  cycle  into distinct  create,  append  and  finalize stages,  we  provide  the  service  layer with  granular  control.  This  enables  us to  incrementally  enforce  size  limits  on every  chunk,  offering  a  more  robust  and manageable  alternative  to  traditional monolithic  upload  methods.  In  our current  architecture,  incoming  RPC requests  pass  through  a  multi-stage filtering  process  before  reaching  the core  service  logic.  The  first  stage  is gate  1,  which  focuses  on  request identification.  This  gate  always succeeds  and  is  responsible  for injecting  a  timeordered  UYU  ID  version  7 into  both  extensions  and  tracing  spans. By  assigning  this  unique  identifier  at the  very  edge  of  the  system,  we  ensure that  every  single  request,  even  those that  are  ultimately  rejected,  is permanently  trackable  throughout  our logs. A  significant architectural  advantage  of  this  design lies  in  our  log  sequencing  strategy. Because  UYU  ID  version  7  is  inherently timeordered,  our  logs  naturally  sort themselves  chronologically  by  ID.  This enables  efficient,  streamlined  debugging and  observability  without  the  need  for  a heavy  centralized  trace  collector.
